# 개발 진행 가이드

## 목적

요구사항 정리 → 설계 → 구현·검증 → 자체 점검을 단계별로 수행한다.
각 단계의 결과를 작업 문서에 갱신하고 사용자 승인을 받은 뒤 다음 단계로 진행한다.
기능 추가·버그 수정·리팩터링 등 개발 작업 전반을 다루며, 변경 크기로 적용 범위를 제한하지 않는다.
전체 흐름과 문서·승인 상태는 개발 진행이 관리하고, 필요한 전문 작업은 해당 스킬을 참조한다.
기존 작업 문서를 단계별로 보완하여 기대 동작과 실행 근거를 남긴다.

## 단계별 승인과 문서 갱신

- 기존 관련 작업 문서를 사용하고, 없으면 단일 통합 명세를 만든다. 각 단계에서 실제 수행한 내용만 갱신한다.
- 단계 결과, 주요 결정·가정, 남은 쟁점을 문서에 반영한 뒤 링크와 함께 승인을 요청한다. 승인 요청은 검토 가능한 결과를 만든 후에 한다.
- 승인이 없거나 수정 의견만 전달되면 현재 단계를 보완하고 다시 승인을 요청한다. 응답 대기 시간이나 최초의 구현 요청을 다음 단계의 승인으로 간주하지 않는다.
- 승인한 단계와 사용자 응답의 근거를 짧게 기록한다. 다음 단계부터 승인된 내용을 재사용하며 같은 범위의 승인을 반복해서 요청하지 않는다.
- 승인한 요구사항·설계를 실질적으로 바꿔야 하면 변경 내용과 영향을 문서에 반영하고 해당 변경의 승인을 받은 뒤 의존 작업을 진행한다.
- 문서의 전체 채택 상태와 단계별 승인·실행 결과를 구분한다. 요구사항 승인만으로 구현·검증 완료나 문서 전체의 채택을 표시하지 않는다.
- 사용자가 명시적으로 여러 단계를 함께 승인하거나 승인 방식을 바꾸면 그 범위와 방식을 따른다. 커밋·PR·게시·배포 권한은 단계 승인과 별개다.

## 수행 깊이 판단

사용자가 `개발 진행` 스킬 또는 `$development-workflow` 사용을 명시적으로 요청했을 때만 이 절차를 적용한다.
일반적인 개발·수정·작업 진행 요청만으로 자동 적용하지 않는다.
사용자가 요구사항·설계·리뷰만 요청했다면 그 범위까지만 수행한다.

사용자 요청과 관련 코드·호출자·기존 명세에서 불확실성·영향 범위·복구 위험을 살펴 각 단계의 깊이와 필요한 전문 작업을 정한다.
줄 수·파일 수·예상 시간만으로 수행 깊이를 정하지 않는다.

| 판단할 내용 | 필요한 보완 |
| --- | --- |
| 현재 동작·원인·호출자·영향 범위가 불명확함 | 관련 코드·문서·실행 경로 조사 |
| 목적·범위·시나리오·정책·예외에 중요한 미결정 사항이 있음 | 요구사항과 관찰 가능한 완료 조건 구체화 |
| 책임·모듈 경계·주요 흐름·공개 계약이 바뀜 | 책임·계약·호환성과 변경 영향 설계 |
| 데이터 변환·삭제, 권한 경계, 외부 상태에 영향이 있음 | 실패·복구 조건과 필요한 승인 검토 |
| 기존 도구로 앱 수준 동작을 검증하기 어려움 | 검증 환경·도구·실행 과정 구성 |

기대 동작과 영향이 명확한 작업은 각 단계의 판단과 근거를 짧게 정리한다.
복잡한 작업은 아래 전문 스킬 참조 기준에 따라 필요한 내용을 구체화한다.
작업이 단순하다는 이유로 승인된 계약과 필수 검증을 생략하거나, 복잡하다는 이유로 모든 스킬을 실행하지 않는다.

## 수행 흐름

### 1. 기대 동작과 범위를 정리한다

- 사용자 요청, 관련 기존 명세와 코드에서 변경 전후의 동작을 확인한다.
- 목적, 이번 범위, 관찰 가능한 완료 조건을 짧게 정리한다. 버그는 재현 조건과 기대 결과를 기준으로 삼는다.
- 기존 요구사항·설계가 있으면 해당 기준을 재사용한다. 바뀌는 계약은 기존 문서에도 반영한다.
- 영향이 작고 되돌리기 쉬운 세부사항은 기존 관례에 따라 결정한다. 중요한 가정에는 근거와 `(확인)`, `(추론)`, `(추측)`을 표시한다.
- 범위·정책·큰 위험을 바꾸는 미결정 사항은 기존 합의로 해결할 수 없을 때 질문한다.
- 요구사항·완료 조건·미결정 사항을 문서에 반영하고 승인을 요청한다. 승인 전에는 설계·구현으로 넘어가지 않는다.

### 2. 변경안과 검증 방법을 정한다

- 재사용할 코드, 수정할 책임·경로, 관련 호출자와 회귀 위험을 확인한다.
- 무엇을 어떻게 바꿀지와 왜 그 방식이면 충분한지를 짧게 정리한다. 대안 비교나 도식은 판단에 도움이 될 때만 추가한다.
- 완료 조건을 어떤 실행·기존 테스트로 확인할지 먼저 정한다. 정상 동작 외에 이번 변경과 관련된 실패·경계 조건을 포함한다.
- 책임·경계·계약 조정이 필요하면 근거와 영향을 검토하고, 전문 설계가 필요하면 아래 참조 기준을 적용한다.
- API·환경변수 규칙·오류 동작 등 이번 변경의 계약과 선택 이유·검증 방법을 문서에 반영하고 설계 승인을 요청한다. 승인 전에는 구현하지 않는다.

### 3. 구현하고 실행으로 확인한다

- [구현 가이드](../../architecture/guide-impl.md)와 [테스트·검증 가이드](../../architecture/guide-test.md)를 읽고 적용한다.
- 필요한 범위만 수정하고, 기존 사용자 변경을 보존한다. 관련 없는 정리·추상화·의존성 도입을 섞지 않는다.
- 기존 검증을 우선 재사용한다. 재현된 결함이나 변경 계약을 의미 있게 보호할 필요가 있으면 테스트를 추가·보완한다.
- 프로젝트에서 요구하는 검사와 변경에 맞는 실행 검증을 수행한다.
- 실행 실패·환경 문제·미실행을 구분한다. 검증할 수 없으면 사유와 미확인 범위를 남기고 완료 조건 충족을 단정하지 않는다.
- 구현 결과와 실제 검증 명령·결과·남은 사항을 문서에 반영하고 승인을 요청한다. 승인 후 자체 점검으로 진행한다.

### 4. 최종 diff를 자체 점검한다

- 완료 조건과 최종 변경을 대조하고, 관련 호출자·오류 처리·부작용·회귀 위험·불필요한 변경을 확인한다.
- 발견한 결함을 수정하면 영향받는 검증을 다시 수행한다.
- 이 자체 점검은 별도 평가자에 의한 독립 리뷰가 아니다. 품질 점수·리스크 등급·정식 리뷰 통과 판정을 산정하지 않는다.
- 사용자가 정식 코드 리뷰를 요청했거나 프로젝트에서 요구하면 [code-review](../../../.agents/skills/code-review/SKILL.md)를 적용한다. 그때는 선행 검사와 평가 기준을 포함한 해당 절차를 따른다.
- 점검 결과·수정 조치·재검증·남은 사항을 문서에 반영하고 최종 확인을 요청한다.

### 5. 결과와 근거를 남긴다

- 변경 결과, 실행한 검증과 결과, 자체 점검에서 남은 문제, 미확인 범위를 보고한다.
- 실행 검증과 자체 점검에서 중대한 문제가 없고 완료 조건을 충족했을 때 구현 완료로 보고한다. 미충족 조건이 있으면 남은 작업과 필요한 조치를 명시한다.
- 커밋·PR·게시·배포는 이 흐름의 자동 후속 단계로 추가하지 않고 사용자 요청 범위를 따른다.

## 기록 방식

이미 작업 문서나 이슈·PR이 있으면 그곳의 관련 내용을 갱신하고 같은 근거를 중복 작성하지 않는다.
새 문서가 필요하면 [문서 관리 가이드](../doc-mgmt.md)에 따라 관련 주제의 디렉터리에 작성한다. 요구사항은 `req-요구사항명.md`, 설계·계획은 `plan-요구사항명.md`로 구분한다.
ID·상태·메타데이터는 기본 작성 항목으로 요구하지 않는다. 변경된 계약은 기존 관련 문서에도 반영한다.

별도 `requirements.md`, `plan.md`, `verification.md`, `review.md`를 일괄 생성하지 않는다.
전문 스킬에서 별도 산출물이 필요하면 기존 문서와 역할을 구분하여 연결하고 같은 내용을 중복 작성하지 않는다.
문서에는 현재 단계와 승인·대기 상태를 표시하고, 각 단계에 도달했을 때 해당 결과를 추가한다.
아래는 점진적으로 갖추는 구성 예시이며, 미수행 단계의 결과를 미리 채우지 않는다.

```markdown
## 단계별 진행 상태

- 요구사항 정리 / 설계 / 구현·검증 / 자체 점검: 미착수·검토 대기·승인, 승인 근거

## 요구사항과 완료 조건

- 변경 전후의 기대 동작, 이번 범위와 확인할 조건

## 설계

- 활용할 기존 구조, 계약·변경 방향, 선택 이유와 중요한 가정

## 구현·검증 결과

- 실제 변경, 실행한 명령·조건과 결과, 검증한 범위

## 자체 점검

- 최종 diff에서 확인한 문제와 조치
- 남은 문제·미확인 범위 또는 없음
```

## 전문 스킬 참조

현재 단계에서 해결할 불확실성이나 필요한 전문 결과가 있을 때 해당 스킬을 읽고 적용한다.
전체 흐름을 다른 스킬로 넘기지 않고, 개발 진행이 현재 단계·다음 작업·문서·승인 상태·완료 조건을 계속 관리한다.
전문 스킬은 아래 책임에 해당하는 결과를 제공하며, 개발 진행은 그 결과를 작업 문서와 다음 단계에 연결한다.

| 필요한 작업 | 참조할 스킬 |
| --- | --- |
| 현재 구조·동작·원인·영향 범위 조사 | [explain](../../../.agents/skills/explain/SKILL.md) |
| 목적·시나리오·정책·예외·완료 조건 구체화 | [req-def](../../../.agents/skills/req-def/SKILL.md) |
| 책임·경계·계약·호환성·복구 설계 | [plan](../../../.agents/skills/plan/SKILL.md) |
| 앱 수준 검증 환경·도구·과정 구성 | [create-verification](../../../.agents/skills/create-verification/SKILL.md) |
| 요청받거나 프로젝트에서 요구하는 정식 품질·리스크 평가 | [code-review](../../../.agents/skills/code-review/SKILL.md) |

모든 스킬을 처음부터 순서대로 실행하지 않는다. 기존 결과가 충분하면 재사용한다.
전문 스킬의 상세 절차를 이 가이드에 중복 정의하지 않고 해당 스킬을 따른다.
전문 스킬을 참조해도 기존 문서와 승인 근거를 이어받으며, 같은 범위의 승인 요청을 반복하거나 미승인 단계를 건너뛰지 않는다.
새로운 중요 결정이나 추가 권한이 필요하면 그 결정에 의존하는 작업을 보류하고, 무엇이 왜 필요한지 구체적으로 확인한다.
커밋·PR·게시·배포는 전문 스킬 참조와 별개로 사용자 요청 범위를 따른다.
