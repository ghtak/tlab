# 기능 구상 가이드

## 목적과 범위

논의 대상에서 무엇을 지원하고 어떤 일을 다뤄야 하는지, 항목 사이의 관계는 무엇인지 간략히 정리한다.
큰 기능 영역과 개별 기능의 할 일 목록에 같은 방식을 적용하며, 별도 관리 체계로 나누지 않는다.
상세 내용은 관련 요구사항·설계 문서에 두어 논의 범위와 지역성을 유지한다. (확인: 사용자 지정 방향)

## 추상화와 변경 제안

- 답변은 목적·책임·기능 범위·관계를 중심으로 구성한다. 개별 사례는 공통 기능으로 묶되, 사용자가 제시한 의미와 제약을 일반화 과정에서 없애지 않는다.
- 무엇을 제공하고 누가 책임지며 어디까지 다루는지는 명확히 한다. 추상화는 표현을 모호하게 만드는 것이 아니라 현재 결정에 맞는 수준으로 논점을 묶는 것이다.
- 변경 제안은 상위 수준에서 무엇을 추가·제외·이동할지와 그 이유를 먼저 설명한다. 세부 항목의 긴 목록으로 변경 방향을 대신하지 않는다.
- 세부 시나리오·정책·예외·처리 흐름·구현 방식은 현재 범위나 책임 경계 판단에 필요하거나 사용자가 상세화를 요청한 경우에 다룬다. 현재 결정에 필요하지 않은 상세 논점은 질문이나 할 일로 과도하게 확장하지 않는다. (확인: 사용자 지정 방향)

## 참조와 기록 범위

- 기본은 사용자와의 대화와 일반적인 개념 지식으로 시작한다. 이 가이드와 연결된 기능 구상 스킬 외의 자료는 자동으로 참조하지 않는다.
- 자료는 사용자가 명시적으로 요청한 범위에서 확인한다. 추가 참조가 필요하면 대상·목적을 설명하고 동의 답변을 받은 뒤 확인한다. 이미 허용한 범위는 반복해서 묻지 않는다.
- 앞서 확인한 구현 정보도 사용자가 이번 구상의 전제로 지정하지 않으면 근거로 사용하지 않는다. 사용자 의도·현재 구현·AI 제안을 구분한다.
- 결과는 대화에 유지한다. 저장을 요청받으면 사용자 지정 위치나 해당 기능의 기존 문서에 정리하고, 필요할 때 `docs/specs/<기능>/index.md` 같은 문서를 사용한다. [문서 관리 규칙](../document-management/index.md)은 해당 범위에 적용한다.
- `docs/notes`는 사용자가 명시적으로 참조를 요청한 문서만 읽으며 확정 요구사항으로 취급하지 않는다. (확인: 사용자 지정 경계·추론)

## 대화 진행

1. **의도 파악**: 목적·대상·지원 범위·제약·나중에 정할 사항을 짧게 정리한다.
2. **목록 정리**: 필요한 기능·할 일을 한 줄 설명과 함께 나열하고, 관련 항목·선행 조건과 필요한 흐름을 정리한다.
3. **검토·조정**: 필요성·대안·누락·중복을 살펴 항목과 범위를 조정하고, 남은 질문을 정리한다. (제안·추론)

이미 명확한 내용을 다시 묻지 않고, 현재 정보로 초안을 만들 수 있으면 먼저 제시한다.
중요한 질문 한두 개씩 다루며 필요한 단계로 돌아갈 수 있다. 단계별 승인을 강제하지 않는다.
명시된 지원 범위와 새 제안은 구분하고, 필요할 때 `포함·후보·보류·제외`를 표시한다.
이 표시는 지원 범위를 판단하기 위한 것이며 별도 개발 진행 상태를 관리하는 항목은 아니다.
보류는 미지원을 뜻하지 않으며, 제안을 확정 요구사항으로 취급하지 않는다. 주요 판단에는 `(확인)`, `(추론)`, `(추측)`을 표시한다. (제안·추론)

## 상세 내용과의 연결

구상에서는 논의 대상의 기능·할 일·관계와 열린 질문을 정리한다.
각 기능의 시나리오·정책·예외·검증 조건은 요구사항 논의에서, DB·API·JWT 등의 구체적인 구조와 계약은 설계 논의에서 다룬다. (제안·추론)

상세 논점이 나오면 현재 범위나 책임 경계 판단에 필요한지 먼저 살핀다. 필요한 논점만 관련 항목에 질문과 문서 링크로 남기며, 나중에 정할 세부 사항을 모두 열린 질문으로 나열하지 않는다.
DB나 JWT 같은 기술 이름만으로 작업을 기계적으로 나누지 않고, 목적·소유 책임·함께 결정할 범위를 기준으로 구분한다.
사용자가 상세화를 요청하면 해당 항목의 목적·범위·이미 정한 내용·열린 질문을 필요한 만큼 전달한다.
상세 결정과 검증 결과는 해당 문서에서 관리하고, 목록에는 이해에 필요한 설명과 연결만 유지한다.
하위 결과를 상위 개요에 수집하거나 상태를 집계하는 절차를 두지 않는다. 범위나 관계가 달라지면 관련 항목만 조정한다. (제안·추론)

## 결과물의 수준

작은 구상은 목록만으로 시작하고, 다음 항목을 필요한 만큼 유지한다. (제안·추론)

| 기능·할 일 | 한 줄 설명·범위 | 관련 항목·선행 조건 | 남은 질문·문서 링크 |
| --- | --- | --- | --- |

목적·제약, 주요 흐름과 열린 질문을 함께 적을 수 있다.
상세 시나리오·필드·테이블·API·검증 조건을 채우는 양식으로 확대하지 않는다. (제안·추론)

예를 들어 계정 관리의 범위를 논의한다면 가입·로그인·탈퇴 등 사용자 목적에 따라 묶고, 로그인 수단 연결·계정 통합은 서비스 목적에 따라 후속 과제로 분리할 수 있다. 더 작은 기능을 다룰 때도 그 범위의 목적·책임·관계를 먼저 정리한다. 이는 구체적인 기능 범위를 고정하는 규칙이 아니다. (예시·추론)

현재 범위에서 다룰 일·관계와 남은 질문이 드러나면 구상 수준에서 마칠 수 있다.
모든 기능의 요구사항이나 설계를 완료하는 것을 종료 조건으로 삼지 않는다. (제안·추론)
