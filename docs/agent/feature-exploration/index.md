# 기능 구상 가이드

## 목적과 범위

사용자가 설명한 목적·지원 범위·제약을 바탕으로 필요한 기능 목록과 간단한 흐름의 초안을 만들고,
대화를 통해 목록 수준에서 추가·통합·분리·범위 조정을 진행한다.
개별 기능을 요구사항으로 상세화하기 전에 무엇을 지원할지 가늠하는 과정이다. (확인: 사용자 지정 목적)

기능과 시나리오를 처음부터 엄격히 구분하지 않는다.
사용자가 하려는 일과 이를 위해 시스템이 제공할 일을 읽기 쉬운 이름과 한 줄 설명으로 정리한다.
계정 종류나 관리체계는 기능 목록을 검토하면서 필요한 구분이 드러날 때 후보로 정리한다. (제안·추론)

## 대화의 근거와 참조 범위

- 사용자가 구상 대화에서 제공한 정보와 일반적인 개념 지식을 바탕으로 진행한다.
- 이 가이드와 이를 연결하는 `feature-exploration` 스킬 외의 스킬·저장소·내부 문서·외부 자료는 자동으로 참조하지 않는다. 사용자가 참조를 요청하면 지정한 범위에서 활용한다.
- 앞선 대화에서 확인한 구현 정보도 사용자가 이번 구상의 전제로 지정하지 않으면 판단 근거에 넣지 않는다.
- 현재 구현 여부나 제공자별 실제 지원 조건은 조사 없이 확인된 사실로 표현하지 않는다. 필요하면 확인할 항목으로 남긴다.
- 기능 목록 작성에 필요하지 않은 코드 탐색, 도구 실행, 설계·요구사항 절차로 자동 전환하지 않는다. (제안·추론)

현재 시스템에 맞춰 정리해 달라는 요청과 자유롭게 구상해 달라는 요청을 구분한다.
자료 조사나 구현 대조가 필요해지면 그 이유를 설명하고, 사용자 요청에 따라 별도 작업으로 연결한다. (제안·추론)

## 진행 방식

### 1. 입력에서 기준 추리기

사용자의 설명에서 목적, 지원할 대상·방식, 제약, 나중에 정할 사항을 짧게 정리한다.
계정 종류·인증 수단·권한처럼 의미가 다를 수 있는 표현은 필요한 만큼만 구분한다.
현재 정보로 초안을 만들 수 있으면 먼저 제시하고, 목록의 방향을 바꾸는 질문만 우선한다. (제안·추론)

### 2. 기능 목록과 간단한 흐름 제안

사용자가 명시한 기능과 이를 성립시키는 데 필요해 보이는 기능을 함께 정리한다.
후보는 사용자 확정 범위와 구분하고, 선택 기능은 필요한 이유를 덧붙인다.
큰 주제는 이해에 도움이 될 때만 묶고, 모든 항목을 미리 잘게 나누지 않는다. (제안·추론)

흐름은 기능의 연결이나 누락을 확인할 정도로 작성한다.
예를 들어 `가입 → 로그인 → 계정 사용 → 탈퇴`처럼 큰 순서를 제시하고,
필요하면 특정 기능의 흐름을 두세 단계로 덧붙인다.
모든 기능의 정상·실패 분기를 상세 시나리오로 전개하지 않는다. (제안·추론)

### 3. 목록 수준에서 상세화

한 번에 중요한 질문 한두 개를 다루며 다음을 조정한다. (제안·추론)

- 누락된 기능을 추가하거나 목적이 겹치는 항목을 통합한다.
- 한 항목에 서로 다른 목표가 섞이면 분리한다.
- 기능별 대상, 지원 방식, 포함·제외 범위를 짧게 보완한다.
- 다른 기능이 먼저 필요한 관계나 흐름의 빈틈을 확인한다.
- 계정 연결처럼 제품 정책이 필요한 기능은 선택지와 판단할 질문을 남긴다.

답변을 받을 때마다 최신 목록과 흐름을 갱신한다.
사용자가 결정하지 않은 항목을 임의로 확정하지 않고, 변경된 내용과 남은 질문을 짧게 설명한다.
제안의 근거가 약하거나 불필요한 기능이면 추가를 유보하고, 사용자 의견과 다른 판단도 이유와 함께 제시한다. (제안·추론)

## 결과물의 수준

대화에서는 다음 구성을 기본으로 하되, 작은 구상은 목록만으로 시작할 수 있다. (제안·추론)

1. **현재 범위**: 사용자가 제시한 조건과 나중에 정할 사항.
2. **기능 목록**: 기능명, 한 줄 설명, 필요할 때 범위·상태.
3. **간단한 흐름**: 기능 사이의 연결과 중요한 선행 관계.
4. **열린 질문**: 목록이나 범위를 정하는 데 필요한 다음 질문.

항목의 상태는 필요할 때 `포함`, `후보`, `보류`, `제외`로 구분한다.
사용자가 지원한다고 명시한 범위는 포함으로 반영하고, 새로 도출한 기능은 제안·후보임을 드러낸다.
`보류`는 나중에 검토할 항목이며, 제품에서 지원하지 않는다는 뜻으로 사용하지 않는다. (제안·추론)

목록 수준의 상세화는 무엇을 지원하는지와 기능 간 관계를 설명하는 데 집중한다.
필드별 검증 규칙, 오류별 처리, 상세 권한 정책과 수용 조건은 후속 요구사항 단계에서 다룬다.
API·DB·프레임워크 등 구현 방식은 사용자가 현재 제약으로 지정한 범위를 넘어서 결정하지 않는다. (제안·추론)

## 사용 예시

다음은 가이드의 사용 예시이며, 프로젝트의 실제 요구사항이나 확정 기능 목록이 아니다. (예시·추측)

> 계정 기능을 지원할 거야. 로컬 계정과 구글·카카오 소셜 계정을 지원하고 이메일 기반으로 할 거야.
> 실제 웹 연동 방식은 이후에 정할 거야. 필요한 기능 목록과 간단한 흐름부터 정리해줘.

이 입력에서는 로컬·소셜 방식과 이메일 기반이라는 조건을 정리하고,
세션·JWT-cookie 등 웹 연동 방식은 이후에 정할 사항으로 유지한다.
목록은 예를 들어 다음 수준에서 시작한다. (예시·추론)

| 기능 | 설명·범위 | 상태 |
| --- | --- | --- |
| 로컬 가입·로그인 | 이메일 기반 로컬 가입과 로그인을 지원한다. 비밀번호 사용 여부는 확인한다. | 포함 |
| 소셜 가입·로그인 | 구글·카카오를 통한 가입과 로그인을 지원한다. | 포함 |
| 이메일 확인 | 이메일 소유 확인이 필요한 경우와 시점을 정한다. | 후보 |
| 로그인 수단 연결·해제 | 한 사용자가 로컬·소셜 수단을 함께 사용할 수 있을지 검토한다. | 후보 |
| 계정 복구 | 로컬 인증 방식에 맞는 복구 기능의 필요성을 검토한다. | 후보 |
| 로그아웃 | 로그인 상태를 종료하는 기능을 검토한다. 웹 연동 방식은 이후에 정한다. | 후보 |
| 계정 탈퇴 | 계정 사용을 끝내는 기능과 범위를 검토한다. | 후보 |
| 웹 인증 연동 | 세션·JWT-cookie 등 구체적인 연동 방식을 정한다. | 보류 |

큰 흐름의 초안은 `가입 또는 소셜 인증 → 계정 식별·생성 → 로그인 완료 → 계정 사용` 정도로 제시한다.
소셜 제공자가 항상 이메일을 반환한다거나 같은 이메일이면 자동으로 계정을 합친다고 가정하지 않는다.
예를 들어 “이메일을 계정 식별 기준으로 쓸지, 연락처로 쓸지”,
“동일 사용자의 로컬·소셜 로그인 수단을 연결할지”를 다음 질문으로 좁힐 수 있다. (예시·추론)

## 후속 단계와 경계

구상의 결과는 대화에 유지하며, 별도 문서 저장은 사용자가 요청할 때 수행한다.
기능 목록을 작성했다는 이유로 확정 요구사항이나 채택된 설계로 취급하지 않는다.
다음 단계로 넘어갈 때는 합의한 범위, 후보·보류 항목과 열린 질문을 함께 전달한다. (제안·추론)

- 기능의 흐름·정책·예외·검증 조건을 구체화하려면 요구사항 정의 단계로 연결한다.
- 현재 구현과 차이를 확인하려면 조사 단계로 연결한다.
- 구현 구조와 기술 선택을 정하려면 설계 단계로 연결한다. (제안·추론)

후속 단계는 사용자 요청에 따라 시작하며, 이 가이드를 적용하는 동안 해당 스킬이나 문서를 미리 읽지 않는다. (제안·추론)
