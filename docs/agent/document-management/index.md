# 문서 관리 규칙

AI가 요구사항·설계·검증·의사결정 문서를 자산으로 관리할 때 참조하는 구조와 규칙이다.
Markdown 파일을 직접 읽고 수정하며, 내용과 상태는 사용자 요청과 기존 합의에 따라 판단한다.

## AI 작업 절차

1. 파일 목록과 문서 ID를 검색하여 대상 문서를 찾는다. 같은 ID가 이미 있으면 새 문서를 만들기 전에 용도를 확인한다.
2. 필요한 문서·절과 연결 문서를 읽고 현재 범위·상태·의존 관계를 확인한다.
3. 새 문서는 작성 양식을 참고하여 직접 작성한다. 기존 문서는 필요한 부분만 수정한다.
4. 문서 ID를 검색하여 역참조와 변경 영향을 확인하고, 관련 요구사항·설계·검증·링크를 함께 보완한다.
5. 변경 내용을 diff로 검토하고 아래 확인 항목을 점검한다. 이미 읽은 뒤 다른 수정이 있었으면 최신 내용을 확인하여 반영한다.

현재는 별도 관리 CLI·DB·인덱스를 두지 않는다.
검색·반복 편집·검증에서 실제로 반복되는 문제가 확인되면 필요한 기능만 도구로 추가한다.

## 적용 범위와 저장 경로

관리 대상은 합의와 구현 판단의 근거로 사용하는 요구사항·설계·검증·주요 의사결정 문서다.
작성 방법과 양식은 `docs/agent`, 실제 산출물은 `docs/specs`에 둔다.
`docs/notes`는 사용자가 명시적으로 참조를 요청한 문서만 읽으며, 읽은 내용을 확정 요구사항으로 간주하지 않는다.
기존 노트나 문서를 자동으로 이전하지 않는다.

실제 산출물은 기능 안에서 사용자 행위별로 모은다.
결정사항은 기능의 `decisions/`에 모으고, 여러 기능에 공통인 결정은 `docs/specs/decisions/`에 둔다.

```text
docs/
├── agent/
│   ├── document-management/
│   │   └── index.md
│   └── requirements-definition/
│       ├── index.md
│       └── template.md
├── specs/
│   ├── decisions/                    # 여러 기능에 공통인 결정
│   └── orders/
│       ├── index.md                  # 선택: 기능 개요·행위 목록
│       ├── decisions/
│       │   ├── DEC-ORDERS-001-access-policy.md
│       │   └── DEC-ORDERS-002-delivery-provider.md
│       ├── view-order/
│       │   ├── requirements.md
│       │   └── plan.md
│       ├── track-delivery/
│       │   ├── requirements.md
│       │   ├── plan.md
│       │   └── verification.md       # 선택: 별도 검증 기록
│       └── cancel-order/
│           ├── requirements.md
│           └── plan.md
└── notes/
```

위 `specs` 이하 경로와 파일은 구조 예시다. 실제 문서는 작업 범위에 맞춰 만든다.
폴더 이름은 기능·행위를 설명하는 소문자 영문과 하이픈을 사용한다.
행위는 주문 조회·배송 조회·주문 취소처럼 사용자가 달성하려는 목표로 나눈다.
정상·실패·권한 없음은 해당 행위의 시나리오로 관리하며, 내부 API나 처리 단계로 경로를 나누지 않는다.

공통 요구사항·설계는 기능 루트에 한 번 작성하고 행위별 문서에서 참조한다.
특정 행위에만 해당하는 결정도 기능의 `decisions/`에 두고 적용 대상과 관련 문서·요구사항을 명시한다.
별도 결정 문서는 대안과 선택 이유를 보존할 가치가 있는 주요 결정에 한해 작성한다.

작은 기능은 한 문서에서 시작하고 필요할 때 행위·문서 종류별로 분리한다.
`index.md`와 검증 문서는 탐색이나 기록 분리가 필요할 때만 만든다.
테스트·CI 기록으로 충분한 검증 근거를 문서에 복제하지 않는다.

## 식별자

문서 ID는 문서 전체를, 개별 요구사항 ID는 설계·검증에서 참조할 조건을 식별한다.
ID는 저장소 안에서 유일하게 관리하고, 경로·제목이 바뀌어도 유지한다.
폐기한 ID는 재사용하지 않으며, 과거 사용 여부가 불명확하면 Git 이력을 확인한다.

| 대상 | ID 예시 | 용도 |
| --- | --- | --- |
| 요구사항 문서 | `REQ-ORDERS-TRACK-DELIVERY` | 요구사항 집합 |
| 설계 문서 | `PLN-ORDERS-TRACK-DELIVERY` | 해당 설계·계획 |
| 통합 명세 문서 | `SPEC-ORDERS-TRACK-DELIVERY` | 요구사항·설계 통합 |
| 검증 문서 | `VER-ORDERS-TRACK-DELIVERY` | 검증 결과·근거 |
| 기능의 의사결정 | `DEC-ORDERS-001` | 기능의 선택 이유·대안·결과 |
| 공통 의사결정 | `DEC-COMMON-001` | 여러 기능의 공통 결정 |
| 개별 요구사항 | `REQ-ORDERS-TRACK-DELIVERY-001` | 특정 동작·정책·제약 |

문서 종류와 기능·행위 키를 조합하고, 개별 요구사항과 의사결정에는 일련번호를 추가한다.
요구사항 순서가 바뀌어도 번호를 다시 매기지 않는다.
통합 명세 안에서도 개별 요구사항에는 `REQ-...` ID를 부여한다.

단순한 문구 수정은 기존 ID를 유지한다.
문서나 요구사항의 분리·통합으로 의미가 바뀌면 새 ID를 부여하고 기존 대상과의 관계를 기록한다.

## 공통 메타데이터

자산 문서 첫 부분에 YAML 메타데이터를 둔다. 필수 필드는 `id`, `status`이며 선택 필드는 `owner`다.
문서 종류는 접두어로 구분하며 `type`을 중복 기록하지 않는다.
생성·수정 일자와 생성자·수정자는 Git 이력으로 확인한다.
관계 정보는 YAML에 넣지 않고 Markdown의 `연결 문서` 표에 둔다.

```yaml
---
id: PLN-ORDERS-TRACK-DELIVERY
status: draft
---
```

| 필드 | 의미 |
| --- | --- |
| `id` | 문서의 고유 식별자 |
| `status` | `draft`, `accepted`, `retired` |
| `owner` | 선택: 현재 문서 관리 책임자. Git 작성자와 구분 |

필드는 단순한 문자열로 작성하고, 새 필드는 실제 관리 필요가 있을 때 공통 규칙에 추가한다.
탐색용 `index.md`에는 메타데이터를 생략할 수 있다.

## 참조와 관계

문서 제목 아래에 `## 연결 문서` 표를 두고 `관계`, `대상`, `설명` 열을 사용한다.
대상은 ID와 상대 경로 링크로 표현한다. 문서 이동 시 ID는 유지하고 참조 경로를 갱신한다.
아래는 가상 예시이며 실제 파일의 존재나 합의를 의미하지 않는다. (추측)

```markdown
---
id: PLN-ORDERS-TRACK-DELIVERY
status: draft
---

# 배송 조회 설계

## 연결 문서

| 관계 | 대상 | 설명 |
| --- | --- | --- |
| realizes | [REQ-ORDERS-TRACK-DELIVERY](./requirements.md) | 배송 조회 요구사항 |
| follows | [DEC-ORDERS-002](../decisions/DEC-ORDERS-002-delivery-provider.md) | 제공자 선택 |
```

| 관계 | 방향 | 의미 |
| --- | --- | --- |
| `realizes` | 설계·통합 명세 → 요구사항·통합 명세 | 요구사항 실현 |
| `verifies` | 검증 기록 → 요구사항·통합 명세 | 요구사항 충족 여부 확인 |
| `follows` | 관련 문서 → 의사결정 | 해당 결정에 따른 내용 |
| `supersedes` | 새 문서 → 이전 문서 | 기존 문서 대체 |

문서 전체의 관계는 연결 표에, 개별 항목의 상세 연결은 본문에 기록한다.
관계를 YAML이나 양쪽 문서에 중복 기록하지 않는다. 역참조는 ID 검색으로 확인한다.
기능의 `index.md`는 탐색용이며 모든 관계를 복제하는 별도 대장으로 만들지 않는다.
일반 본문은 공통 아키텍처 등 저장소 안의 다른 문서·파일도 참조할 수 있다.

개별 요구사항은 ID를 포함한 제목과 ID를 소문자로 바꾼 명시적 앵커를 사용한다.
문서 전체를 참조하는 것만으로 모든 개별 요구사항이 설계·검증되었다고 판단하지 않는다.

```markdown
<a id="req-orders-track-delivery-001"></a>
### REQ-ORDERS-TRACK-DELIVERY-001: 자신의 주문 배송 상태 조회

구매자는 자신의 주문 배송 상태를 조회할 수 있다.

관련 설계에서의 참조:
[REQ-ORDERS-TRACK-DELIVERY-001](./requirements.md#req-orders-track-delivery-001)
```

## 상태와 변경 관리

| 상태 | 의미 | 전환 기준 |
| --- | --- | --- |
| `draft` | 작성·검토 중인 제안 | 새 문서의 초기 상태 |
| `accepted` | 이번 범위의 판단 기준으로 채택 | 사용자 확인 또는 정해진 검토 완료 근거가 있음 |
| `retired` | 현재 기준으로 사용하지 않음 | 폐기 이유와 대체 문서가 있으면 참조를 기록 |

AI가 문서를 작성했다는 이유로 `accepted`로 바꾸지 않는다.
중요한 미결정 사항이 남아 있으면 `draft`를 유지한다.
문서의 채택 상태와 개별 요구사항의 합의 상태·검증 결과·구현 완료 여부를 구분한다.

상태는 YAML에서 직접 수정한다. 채택·폐기 근거는 관련 PR·검토 링크 또는 필요한 수준의 짧은 기록으로 남긴다.
상태 변경마다 고정 형식의 로그를 작성할 필요는 없다. 세부 변경 이력과 작성자는 Git에서 확인한다.

`accepted` 문서의 의미를 바꾸는 제안은 기존 합의와 구분하고, 합의 전까지 새 내용을 채택된 기준으로 취급하지 않는다.
요구사항 변경 시 연결된 설계·검증도 재검토한다.
과거 검증 결과는 대상 코드·문서 버전·실행 근거와 연결하여 최신 결과로 오인하지 않게 한다.

설계 문서(`plan.md`)의 마지막에는 `구현·변경 기록` 절을 둔다.
구현 차수별 요약과 대화·검증 스킬에 따른 변경 기록을 발생 순서대로 하단에 추가한다.
구현 범위·결과, 변경 내용·이유·상태, 관련 검증 근거와 남은 사항을 간략히 기록하고 이전 기록은 보존한다. (확인)

설계 변경은 합의 상태에 맞춰 본문에도 반영한다.
하단 기록은 변경 경위를 제공하며, 세부 코드 변경은 Git 이력으로, 검증 근거는 작업별 `verification.md`로 연결한다.
작성 형태는 [설계 문서 작성 가이드](../create-plan/index.md)를 참조한다. (추론)

## 변경 후 확인

- 문서·요구사항 ID가 중복되지 않고 기존 의미를 유지하는가?
- 메타데이터의 상태가 실제 합의 수준과 일치하는가?
- 관계의 의미·방향과 대상 ID·경로·앵커가 맞는가?
- 이동·수정한 문서의 역참조와 관련 설계·검증을 확인했는가?
- 폐기 문서를 현재 기준으로 참조하거나 과거 검증을 최신 결과로 사용하지 않는가?
- diff에 요청 범위를 벗어난 변경이나 양식의 미치환 자리표시자가 남지 않았는가?

필요한 문서와 연결을 직접 확인한다. 별도 검증 스크립트는 현재 운영의 필수 조건이 아니다.
