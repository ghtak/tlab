# 작은 변경 처리 가이드

## 목적

요구사항 정리(req) → 설계(plan) → 구현(impl) → 리뷰(review)의 핵심 판단을 한 흐름에서 수행한다.
단계마다 별도 스킬·문서·승인을 거치는 비용을 줄이면서, 기대 동작과 실행 근거를 남기는 것이 목적이다.

## 적용 판단

사용자 요청과 관련 코드·호출자·기존 명세를 확인하고 아래 기준으로 판단한다.
줄 수, 파일 수, 예상 시간만으로 작은 작업이라고 결정하지 않는다.

| 약식 처리에 적합 | 정식 절차로 전환할 신호 |
| --- | --- |
| 목적·기대 결과를 짧게 설명할 수 있음 | 목적·범위·주요 정책에 중요한 미결정 사항이 있음 |
| 기존 책임·의존 방향·공개 계약을 유지함 | 책임·모듈 경계·주요 흐름이 바뀌거나 공개 API 호환성에 영향이 있음 |
| 영향받는 호출자와 실행 경로를 확인할 수 있음 | 영향 범위나 외부 소비자의 호환성을 판단하기 어려움 |
| 변경된 계약을 기존 도구로 검증할 수 있음 | 검증을 위해 새 앱 수준 환경·도구나 복잡한 연동 구성이 필요함 |
| 코드 복원으로 기존 동작에 돌아갈 수 있음 | 데이터 변환·삭제, 권한 경계, 외부 상태 등 별도 복구 판단이 필요함 |

예를 들어 기존 반환 계약을 유지하는 분기 오류 수정, 기존 컴포넌트의 작은 표시 기능 추가, 동작을 보존하는 중복 제거는 후보가 된다.
반면 함수 한 줄 수정이어도 권한 검사 제거, 데이터 삭제 정책 변경, 공개 API의 반환 의미 변경이면 약식 대상에서 제외한다. (추론)

단순 오탈자처럼 바로 처리할 수 있는 작업에 이 절차를 강제로 추가하지 않는다.
사용자가 요구사항·설계·리뷰만 요청했다면 그 범위까지만 수행한다.

## 수행 흐름

### 1. 기대 동작과 범위를 정리한다

- 사용자 요청, 관련 기존 명세와 코드에서 변경 전후의 동작을 확인한다.
- 목적, 이번 범위, 관찰 가능한 완료 조건을 짧게 정리한다. 버그는 재현 조건과 기대 결과를 기준으로 삼는다.
- 기존 요구사항·설계가 있으면 해당 기준을 재사용한다. 바뀌는 계약은 기존 문서에도 반영한다.
- 영향이 작고 되돌리기 쉬운 세부사항은 기존 관례에 따라 결정한다. 중요한 가정에는 근거와 `(확인)`, `(추론)`, `(추측)`을 표시한다.
- 범위·정책·큰 위험을 바꾸는 미결정 사항은 기존 합의로 해결할 수 없을 때만 질문한다. 각 단계의 완료를 이유로 승인을 추가하지 않는다.

### 2. 최소 변경안과 검증 방법을 정한다

- 재사용할 코드, 수정할 책임·경로, 관련 호출자와 회귀 위험을 확인한다.
- 무엇을 어떻게 바꿀지와 왜 그 방식이면 충분한지를 짧게 정리한다. 대안 비교나 도식은 판단에 도움이 될 때만 추가한다.
- 완료 조건을 어떤 실행·기존 테스트로 확인할지 먼저 정한다. 정상 동작 외에 이번 변경과 관련된 실패·경계 조건을 포함한다.
- 이 과정에서 약식 범위를 벗어나면 아래 전환 기준을 적용한다.

### 3. 구현하고 실행으로 확인한다

- [구현 가이드](../../architecture/guide-impl.md)와 [단위 테스트 가이드](../../architecture/guide-uint-test.md)를 읽고 적용한다.
- 필요한 범위만 수정하고, 기존 사용자 변경을 보존한다. 관련 없는 정리·추상화·의존성 도입을 섞지 않는다.
- 기존 검증을 우선 재사용한다. 재현된 결함이나 변경 계약을 의미 있게 보호할 필요가 있으면 테스트를 추가·보완한다.
- 프로젝트에서 요구하는 검사와 변경에 맞는 실행 검증을 수행한다. 약식 처리라는 이유로 기존 필수 검사를 생략하지 않는다.
- 실행 실패·환경 문제·미실행을 구분한다. 검증할 수 없으면 사유와 미확인 범위를 남기고 완료 조건 충족을 단정하지 않는다.

### 4. 최종 diff를 자체 점검한다

- 완료 조건과 최종 변경을 대조하고, 관련 호출자·오류 처리·부작용·회귀 위험·불필요한 변경을 확인한다.
- 발견한 결함을 수정하면 영향받는 검증을 다시 수행한다.
- 이 자체 점검은 별도 평가자에 의한 독립 리뷰가 아니다. 품질 점수·리스크 등급·정식 리뷰 통과 판정을 산정하지 않는다.
- 사용자가 정식 코드 리뷰를 요청했거나 프로젝트에서 요구하면 [code-review](../../../.agents/skills/code-review/SKILL.md)를 적용한다. 그때는 선행 검사와 평가 기준을 포함한 해당 절차를 따른다.

### 5. 결과와 근거를 남긴다

- 변경 결과, 실행한 검증과 결과, 자체 점검에서 남은 문제, 미확인 범위를 보고한다.
- 실행 검증과 자체 점검에서 중대한 문제가 없고 완료 조건을 충족했을 때 구현 완료로 보고한다. 미충족 조건이 있으면 남은 작업과 필요한 조치를 명시한다.
- 커밋·PR·게시·배포는 이 흐름의 자동 후속 단계로 추가하지 않고 사용자 요청 범위를 따른다.

## 기록 방식

이미 작업 문서나 이슈·PR이 있으면 그곳의 관련 내용을 갱신하고 같은 근거를 중복 작성하지 않는다.
별도 기록이 필요 없는 작은 수정은 대화의 작업 요약으로 충분하다.
향후 참조할 계약이나 결정이 생기면 [문서 관리 규칙](../document-management/index.md)에 따라 `docs/specs/<기능>/<행위>/spec.md` 같은 단일 통합 명세로 시작한다.
그 경우 `SPEC-...` ID, `draft` 상태, 개별 요구사항 ID·앵커와 필요한 연결 문서를 적용한다. 작은 작업이라는 이유로 기존 문서의 계약 갱신을 생략하지 않는다. (추론)

별도 `requirements.md`, `plan.md`, `verification.md`, `review.md`를 일괄 생성하지 않는다.
대화나 기존 문서에 남길 최소 내용은 다음 정도로 묶는다. 자산 문서로 저장할 때는 공통 메타데이터와 참조 규칙을 추가한다.

```markdown
## 목적과 완료 조건

- 변경 전후의 기대 동작, 이번 범위와 확인할 조건

## 변경 방향과 결과

- 활용할 기존 구조, 선택 이유, 실제 변경과 중요한 가정

## 검증과 자체 점검

- 실행한 명령·조건과 결과, 검증한 범위
- 최종 diff에서 확인한 문제와 조치
- 남은 문제·미확인 범위 또는 없음
```

## 정식 절차로의 전환

전환 시 발견한 문제, 확인된 범위, 추가로 결정할 내용을 먼저 정리한다.
기존 정리와 검증 근거를 재사용하며, 모든 스킬을 처음부터 순서대로 실행하지 않는다.

| 필요한 보완 | 연결할 절차 |
| --- | --- |
| 목적·시나리오·정책·완료 조건 구체화 | [requirements-definition](../../../.agents/skills/requirements-definition/SKILL.md) |
| 책임·경계·계약·호환성·복구 설계 | [create-plan](../../../.agents/skills/create-plan/SKILL.md) |
| 앱 수준 검증 환경·도구·과정 구성 | [create-verification](../../../.agents/skills/create-verification/SKILL.md) |
| 정식 품질·리스크 평가 | [code-review](../../../.agents/skills/code-review/SKILL.md) |

전환 자체를 새 승인 단계로 취급하지 않는다. 이미 구현까지 요청받았고 필요한 판단 근거가 충분하면 해당 범위에서 계속한다.
새로운 중요 결정이나 추가 권한이 필요하면 그 결정에 의존하는 작업을 보류하고, 무엇이 왜 필요한지 구체적으로 확인한다.
