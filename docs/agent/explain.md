# explain

동작 원리/구조에 답하기 위해 코드베이스를 탐색. 아키텍처 관점. 시니어 엔지니어의 신규 시스템 온보딩 레벨의 멘탈 모델 수준. 코드 라인 레벨 수준의 상세 설명은 제외.
문서(`README`, `docs/` 등 마크다운 문서)는 참조하지 않음. 현재 구현의 유일한 근거는 실제 소스 코드. 문서는 사용자의 명시적 요구 시에만 참조.

## output

### 작성 스타일
- 구체적 명명 사용: 추상적인 메타 표현 대신 실제 코드 식별자 명시 (예: "서비스가 클라이언트에 위임" → "`UserService`가 `AuthClient.refresh()`를 호출").
- 복잡성 원인 규명: 구조가 복잡할 경우 현상만 묘사하지 말고 왜 복잡한지(설계 배경/제약)를 설명.
- 단순함 유지: 구조가 단순할 경우 억지로 분량 늘리기(Padding) 금지.
- 비유 절제: 이해를 돕는 적절한 비유가 있을 때만 활용. 억지 비유 금지.
- 불확실성 투명 공개: 미해결 의문점이나 빈틈(Gap)을 확인한 경우 숨기거나 추측으로 메우지 말고 그대로 명시.

다음의 출력 양식에 기반.

# Overview

1~2개 문단 분량. 대상의 정체(What it is), 핵심 역할(What it does), 존재 이유(Why it exists)를 요약. 독자가 이 부분만 읽고도 본문 계속 읽기 여부를 결정할 수 있는 수준으로 작성.

# Key Concepts

후속 내용 이해에 필수적인 주요 타입, 서비스, 추상화 요소 정리. 간략한 정의 위주 작성 (전체 나열 및 과도한 상세 설명 금지).

# How It Works

설명의 핵심이자 가장 비중이 큰 섹션. 실행 흐름(트리거 → 단계별 처리 과정 → 데이터 이동 경로 → 주요 분기점)을 순차적으로 서술.

의사코드(Pseudocode) 대신 자연어 산문체로 작성. 독자가 위치를 찾을 수 있도록 구체적인 파일명과 함수명을 명시하되, 핵심 요점 전달에 필수적인 경우가 아니면 대규모 코드 블록 삽입 금지.

다이어그램 활용: 다수 컴포넌트 간 상호작용이나 다단계 데이터 변환 흐름이 있을 경우 다이어그램 포함.
- 구조화된 흐름(시퀀스, 플로우차트, 컴포넌트 그래프): `mermaid` (` ```mermaid `) 사용.
- 단순한 관계(Mermaid가 과한 경우): ASCII 아트 사용.
- 단순 장식용 다이어그램 배제 — 산문만으로 흐름 파악이 충분하면 생략.

# Code Refs

핵심 파일 및 디렉터리 구조 맵. 실제 작업을 시작하는 데 반드시 필요한 경로만 선별하여 간략히 정리 (전체 트리 나열 금지).

# Pitfalls

직관적이지 않은 동작, 예상 밖의 예외 사항, 히스토리적 맥락, 실수하기 쉬운 함정 정리. 특별히 짚고 넘어갈 요소가 없으면 섹션 전체 생략 (억지 작성 금지).
