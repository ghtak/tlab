# 커밋 가이드

검증 이후의 변경을 의미 있는 단위로 나누고, 유형별 메시지로 커밋.

- 검증: 테스트·정적 검사·리뷰 별도 실행 및 검증 근거 요구 없음.
- 포함 내용 확인: 변경 범위와 staged diff 검토.

## 작업 단위

- 분할 기준: 하나의 작업으로 설명하고 되돌릴 수 있는 단위.
- 함께 포함: 해당 작업의 코드·테스트·관련 spec 문서.
- 별도 분리: 관계없는 변경. 큰 작업은 검증 가능한 단위로 분할.
- 일관성: 각 커밋의 코드와 문서 내용 일치.

## 진행 방식

1. 범위 확인: 사용자 요청, `git status`, staged·unstaged diff, 관련 미추적 파일을 바탕으로 커밋 단위 결정.
2. 메시지 결정: 작업의 주목적에 맞춰 유형과 변경 내용 작성. 구성·메시지 제안만 요청한 경우 여기서 종료.
3. 커밋 생성: 실제 커밋 요청 시 대상 파일·변경 부분을 명시해 스테이징. 최종 staged diff 확인 후 커밋.
4. 결과 보고: 커밋 해시·메시지와 남은 변경 제시. 실패 시 원인 확인 후 커밋 처리 범위에서 해결·재시도.

## 처리 경계

- 기존 staged 변경: 요청 대상인지 확인. 무관한 변경 포함 및 임의 스테이징 해제 금지.
- 변경 혼재: 같은 파일에서 안전하게 분리하기 어려우면 사용자에게 범위 확인.
- hook: 정상 실행, hook·검사 우회 금지.
- 검증 실패: 코드 수정이 필요하면 원인 보고 후 별도 작업으로 처리.
- 기존 커밋 수정·이력 재작성·원격 push: 별도 요청 범위에서만 수행.

## 메시지 형식

- 기본 형식: `<유형>: <변경 내용>`.
- 유형 기준: 작업의 주목적. 기능 추가에 spec·테스트가 포함되어도 `feat` 사용.
- 본문: 변경 이유 설명이 필요한 경우에만 추가.

| 유형 | 용도 |
| --- | --- |
| `feat` | 기능 추가 |
| `fix` | 버그 수정 (`bug` 대신 사용) |
| `refactor` | 동작을 유지하는 구조 개선 |
| `docs` | 문서만 변경 |
| `test` | 테스트만 추가·개선 |
| `chore` | 도구·설정 등 유지보수 |

```text
feat: 설정 파일 로딩 지원
fix: 빈 설정 경로의 오류 처리 수정
refactor: 공통 오류 변환 로직 통합
docs: 작은 변경 처리 가이드 추가
```

## 출력 양식

생성 결과는 아래 형식으로 보고. 여러 커밋은 항목 반복.

```markdown
- `{해시}` `{유형}: {변경 내용}` — 포함한 작업 요약

남은 변경: {미커밋 변경 요약 또는 없음}
```

- 구성·메시지 제안: 해시 없이 커밋별 메시지와 포함할 변경 제시.
- 실패 보고: 실패 원인·현재 처리 상태·필요한 후속 조치 명시.
