# 설계 문서 작성 가이드 초안

## 목적

요구사항 문서나 대화·작업 컨텍스트를 바탕으로 설계 문서를 만든다.
현재 소스와 문서에서 상태·구조를 확인하고, 요구사항을 만족하는 최소안을 제시한 뒤
대화를 통해 아키텍처와 인터페이스 수준으로 구체화한다. (확인)

`create-plan`은 이 설계 과정을 가리킨다.
산출물은 구현할 구조와 계약을 설명하는 설계 문서이며, 작업별 세부 구현 순서는 필요할 때 후속으로 정리한다. (추론)

## 진행 과정

```mermaid
flowchart LR
    A[현재 상태·구조 확인] --> B[목표·설계 범위 정리]
    B --> C[요구사항을 만족하는 최소안]
    C --> D[대화로 검토·구체화]
    D -->|보완| C
    D --> E[구성·경계·인터페이스 계약 정리]
    E -->|중요한 쟁점 발견| D
    E --> F[설계 문서·결정 근거 정리]
```

이미 확인하거나 결정한 내용은 재사용한다.
처음부터 모든 세부사항을 질문하지 않고, 현재 근거로 제시할 수 있는 초안을 만든 뒤 중요한 쟁점을 논의한다. (추론)

### 1. 현재 상태와 구조 확인

관련 요구사항·설계·아키텍처 문서와 현재 소스를 함께 읽는다.
설계 시 [구현 가이드](../../architecture/guide-impl.md)와 [테스트·검증 가이드](../../architecture/guide-test.md)를 참조하여 구현 방향과 검증할 계약·기대 결과에 반영한다.
`tlab-app`의 기능을 설계할 때는 [앱 개발 구조](../../architecture/app-structure.md)를 참조하여 feature·slice의 경계, 시나리오 전용 코드의 배치와 공용 작업의 소유 위치를 검토한다.
진입점, 구성요소의 책임, 의존 관계, 주요 처리·데이터 흐름을 파악한다.
이미 구현된 부분, 변경이 필요한 부분, 재사용할 수 있는 부분을 구분한다. (추론)

확인한 내용에는 관련 파일·문서·코드 위치를 연결한다.
문서와 소스가 다르면 불일치를 표시하고, 소스만으로 실제 실행 결과까지 확인했다고 판단하지 않는다.
설계에 영향을 주는 실행 상태는 필요할 때 직접 확인한다. (추론)

### 2. 목표와 설계 범위 정리

이번 설계로 해결할 문제, 기대하는 동작, 포함·제외 범위와 제약을 정리한다.
요구사항 문서가 있으면 해당 조건을 참조하고, 문서가 없으면 대화·컨텍스트에서 설계의 기준을 짧게 정리한다.
설계를 시작하기 위해 별도 요구사항 문서를 반드시 만들 필요는 없다. (추론)

목표·중요 정책이 모호하거나 서로 충돌하면 확인한다.
영향이 작고 수정하기 쉬운 내용은 가정을 표시하고 진행하며, 가정에 따라 범위를 확대하지 않는다. (추론)

### 3. 요구사항을 만족하는 최소안 제시

기존 구조를 활용하면서 이번 요구사항을 충족하는 가장 단순한 안을 제시한다.
추가·변경할 구성요소와 주요 흐름, 요구사항을 충족하는 방식, 기존 동작에 미치는 영향을 설명한다.
향후 확장 가능성만을 이유로 새로운 계층·서비스·공통 프레임워크를 추가하지 않는다. (추론)

중요한 대안이 있으면 차이와 선택 이유를 짧게 비교한다.
대안 수를 채우기 위해 불필요한 안을 만들지 않고, 최소안이 요구사항·제약을 빠뜨리지 않았는지 확인한다. (추론)

#### 단일 구성요소와 상위 조립

재사용 구성요소는 하나의 독립된 대상을 처리하는 구조를 기본으로 한다.
인스턴스의 개수·선택·조합과 인스턴스 간 실행·종료 정책은 상위 조립 계층에서 관리한다.
단순한 호출 편의만으로 다중 대상 관리 책임을 하위 구성요소에 넣지 않는다. (확인: 사용자 지정 설계 선호)

하위 구성요소가 여러 대상을 내부적으로 관리해야 한다면 공동 소유, 원자적 처리, 자원 공유 등 필요한 이유를 설계에 명시한다.
DB 커넥션 풀처럼 여러 자원의 관리 자체가 구성요소의 책임인 경우는 해당 경계 안에서 관리한다. (확인)

예를 들어 서버는 리스너 하나를 담당하고, HTTP·HTTPS 인스턴스의 선택·조정은 앱에서 수행한다.
이 원칙을 적용하기 위해 기존 구조를 일괄 변경하거나 새로운 관리 프레임워크를 추가하지 않는다. (추론)

### 4. 대화를 통한 정리와 구체화

초안과 함께 결정이 필요한 쟁점, 선택지, 권장안과 이유를 제시한다.
사용자 의견을 기존 요구사항·구조와 대조하여 반영하고, 달라진 결정과 근거를 문서에 갱신한다.
중요한 해석 차이는 논의하되, 이미 합의한 내용을 다시 묻거나 단계마다 승인을 요구하지 않는다. (추론)

제안·합의한 결정·미결정 사항을 구분한다.
새로운 제약으로 요구사항 변경이 필요하면 설계 결정과 구분하여 확인한다. (추론)

### 5. 인터페이스 수준으로 정리

구성요소 사이의 책임과 계약을 이해하고 구현할 수 있는 수준으로 작성한다.
내부 함수나 파일별 상세 로직은 경계·계약을 설명하는 데 필요한 경우에만 포함한다. (추론)

| 구분 | 정리할 내용 |
| --- | --- |
| 아키텍처 구성 | 기존 구조에서 유지·추가·변경할 부분과 주요 흐름 |
| 분리 경계 | 각 영역의 책임, 데이터 소유권, 의존 방향과 경계를 나누는 이유 |
| 구성요소 | 역할, 협력 대상, 담당하는 요구사항 |
| 인터페이스 계약 | 호출자·제공자, 입력·출력, 사전 조건, 오류·실패 처리, 상태 변화·부수 효과 |
| 필요한 추가 계약 | 해당할 때 권한, 트랜잭션, 재시도·중복 처리, 호환성·성능 제약 |

각 인터페이스는 API·이벤트·모듈 호출 등 실제 경계에 맞게 표현한다.
필드·타입·오류 의미 등 구현자마다 해석이 달라질 부분을 구체화하고, 정하지 않은 사항은 미결정으로 남긴다.
구조·분리 경계는 Mermaid 구성도로, 호출 순서가 중요하면 시퀀스 다이어그램으로 설명한다. (추론)

## 설계 문서 구성과 연결

[문서 관리 규칙](../document-management/index.md)에 따라 실제 설계는 해당 작업의 `plan.md`에 작성한다.
예를 들어 `docs/specs/<기능>/<행위>/plan.md`에 두며, 요구사항 문서가 있으면 연결 문서와 개별 조건을 참조한다.
문서 ID는 `PLN-<기능>-<행위>` 형식으로 부여하고, `draft` 상태 등 메타데이터는 기존 규칙을 따른다. (확인)

설계 문서는 아래 구성으로 시작하고 관련 없는 항목은 생략한다. (추론)

```text
설계 문서
  연결 문서
  현재 상태와 구조
  목표·설계 범위·제약
  설계안: 아키텍처·분리 경계·구성요소·주요 흐름
  인터페이스 계약
  결정사항과 근거
  가정·미결정 사항
  구현·변경 기록
    1차 구현 요약
    대화·검증에 따른 변경 기록
    2차 구현 요약
    ...
```

작은 설계는 한 문서로 유지한다.
독립적으로 설명할 필요가 있는 상세 계약이나 구조는 개별 문서로 분리하고 본문에서 링크한다.
주요 결정은 필요할 때 기존 규칙의 `decisions/` 문서로 분리하며, 같은 내용을 여러 문서에 중복 관리하지 않는다. (추론)

앱 기능의 `plan.md`에는 [앱 개발 구조](../../architecture/app-structure.md)를 링크하고,
해당 작업의 대상 feature·slice, 전용 코드의 배치, 공용 계약·스키마 의존성과 변경 영향 범위를 구체적으로 기록한다.
공통 구조 원칙은 복제하지 않고, 다른 배치가 필요하면 그 이유와 영향을 남긴다. (추론)

## 결정사항과 근거

중요한 결정에는 선택한 안, 이유와 근거, 검토한 대안, 영향·제약과 합의 상태를 남긴다.
근거는 요구사항, 확인한 코드·문서, 실행 결과 또는 사용자와의 합의로 연결한다.
대화 전체를 옮기기보다 최종 결정과 그 판단을 이해할 수 있는 내용을 보존한다. (추론)

중요한 사실과 판단에는 `(확인)`, `(추론)`, `(추측)`을 표시한다.
사실 확인 여부와 제안의 합의 상태는 별도로 구분하며, 문서를 작성했다는 이유로 채택된 설계로 처리하지 않는다. (추론)

## 구현 요약과 변경 기록

`plan.md`의 마지막에 `구현·변경 기록` 절을 두고, 구현 차수마다 요약을 추가한다.
대화나 검증 스킬을 통해 발생한 변경도 이 절의 하단에 발생 순서대로 추가한다.
이전 기록을 덮어쓰지 않고 이후 차수와 변경 경위를 이어서 읽을 수 있게 한다. (확인)

구현 차수는 의미 있는 구현·수정 작업 단위로 구분하며 개별 파일 수정마다 나누지 않는다.
구현 요약에는 수행 범위와 결과, 설계와 달라진 내용·이유, 검증 결과와 남은 사항을 짧게 남긴다.
대화·검증에 따른 변경 기록에는 계기, 변경 내용, 판단 근거와 반영·검증 상태를 적는다.
변경을 논의했지만 아직 구현하지 않았다면 제안·합의·미반영 상태를 구분한다. (추론)

아래는 `plan.md` 하단의 작성 형태다. 해당하는 항목만 작성한다. (추론)

```markdown
## 구현·변경 기록

### 1차 구현 요약

- 구현 범위·결과:
- 설계와 달라진 내용·이유:
- 검증 결과: 작업별 verification.md의 해당 결과 링크
- 남은 사항:

### 변경 기록: 대화 또는 검증에서 확인한 주제

- 계기·근거: 사용자와의 논의 또는 검증 스킬의 관찰 결과
- 변경 내용·이유:
- 상태: 제안 / 합의·미반영 / 반영 완료 등
- 관련 구현 차수·검증 근거:

### 2차 구현 요약

- 구현 범위·결과:
- 반영한 변경과 검증 결과:
- 남은 사항:
```

설계가 바뀌면 합의 상태에 맞춰 본문의 구성·계약·결정사항도 갱신하고, 변경 경위는 하단 기록에 남긴다.
세부 검증 절차·관찰 근거는 작업별 `verification.md`를 참조하여 중복하지 않는다.
구현 요약이나 변경 기록을 추가했다는 이유로 문서의 채택 상태나 검증 통과 여부를 바꾸지 않는다. (추론)

## 완료 확인

- 현재 상태와 변경할 구조가 구분되어 있다.
- 목표·범위·제약과 설계안이 연결되고, 대상 요구사항을 충족하는 방식을 설명할 수 있다.
- 구성요소의 책임·분리 경계·의존 관계와 주요 인터페이스 계약이 명확하다.
- 인스턴스의 선택·조합·조정 책임이 상위에 있으며, 하위에서 다중 대상을 관리한다면 그 필요성이 설명되어 있다.
- 주요 결정과 근거, 대화로 변경한 내용이 반영되어 있다.
- 추가 문서의 링크가 연결되고 가정·미결정 사항과 영향이 드러난다.
- 구현 방향을 바꾸는 중요한 미결정 사항이 해소되었거나, 영향을 받는 범위가 보류되어 있다. (추론)
