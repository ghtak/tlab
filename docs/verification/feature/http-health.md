# 앱 HTTP 생존 확인

## 접근과 사전 상태

앱이 실행 중이며 확인할 HTTP 또는 HTTPS 인스턴스의 주소를 알고 있어야 한다.
HTTPS에서는 서버 인증서를 검증할 신뢰 자료가 필요하다. 현재 앱 시작에는 접속 가능한 PostgreSQL URL과 JWT 키·HTTPS TLS 설정이 필요하다. `/health` 요청 자체는 사용자 데이터·계정을 사용하거나 DB readiness를 검사하지 않는다. 준비 방법은 [HTTP 실행 도구](../tools/http/README.md)를 따른다. (확인)
요구사항은 [SPEC-HTTP-APP](../../specs/http/app/spec.md)를 따른다.

## 검증 과정과 기대 결과

1. DB URL·JWT 키·TLS 자료를 준비하고 앱을 시작한다. 필수 HTTP·HTTPS 리스너가 준비되고 앱이 종료되지 않아야 한다.
2. `/health`에 GET 요청을 보낸다. 상태 200, Content-Type `text/plain; charset=utf-8`, 본문 `ok`여야 한다.
3. 같은 경로에 POST를 보낸다. 상태 405여야 한다. HEAD는 200이며 본문이 없어야 한다.
4. 없는 `/heath` 경로를 요청한다. 상태 404여야 한다.
5. HTTPS에서도 인증서 검증을 켠 요청으로 동일한 `/health` 응답을 확인한다.
6. 정적 파일을 설정하면 같은 파일이 활성 HTTP·HTTPS 인스턴스에서 동일하게 제공되어야 한다.
7. 앱에 종료 요청을 전달한다. 리스너가 해제되고 기존 주소로 새 요청이 연결되지 않아야 한다.

준비 실패 경로도 확인한다. 필수 HTTP·HTTPS 설정 중 하나가 누락되거나 전송 방식과 TLS 설정이 맞지 않으면 오류여야 한다.
두 번째 인스턴스의 준비가 실패하면 앞서 준비한 포트가 남지 않아야 한다.

## 판정 범위

`/health` 성공은 앱의 요청 처리 경로가 살아 있다는 의미다. DB·다른 서비스의 readiness나 업무 처리 가능 여부를 대신 검증하지 않는다.
요청 실행 여부와 기대한 상태·본문을 실제로 확인한 결과를 구분한다.
종료 후 미완료 TLS 핸드셰이크의 즉시 차단은 보장 대상에서 제외한다.
