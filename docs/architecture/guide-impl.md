코드를 신규 구현하거나 수정할 때 다음 원칙을 따른다.

- 관련 코드가 있다면 기존 동작과 설계 의도를 확인하고 존중한다.
- 구현 전에 관련 구조와 기존 기능을 확인해 같은 책임의 코드를 중복 작성하지 않는다.
- `tlab-app`의 기능을 추가·수정할 때는 [앱 개발 구조](app-structure.md)를 참조하여 시나리오 전용 코드는 해당 slice에 두고, 공용 정책·작업·스키마를 변경하면 이를 사용하는 다른 slice의 영향을 확인한다.
- 재사용 구성요소의 책임 경계와 인스턴스 조립은 설계 가이드의 [단일 구성요소와 상위 조립](../agent/create-plan/index.md#단일-구성요소와-상위-조립) 원칙을 따른다.
- 기존 기능을 재사용할 때 입력 조건, 결과, 오류 처리와 부작용이 요구사항에 맞는지 확인한다. 차이가 있다면 무리하게 통합하거나 불필요한 추상화를 추가하지 않는다.
- 검증을 추가하기 전에 값의 출처, 이미 보장된 조건, 해당 조건을 책임지는 입력 경계를 확인한다. 검증은 그 책임을 소유한 경계에 두고 소비자마다 반복하지 않는다.
- 신뢰된 생산자가 계약에 맞게 생성하고 무결성이 확인된 데이터는 해당 계약을 신뢰한다. 소비자는 필요한 타입 변환만 수행하며 생산자가 보장한 형식·범위·필수 조건을 다시 검증하지 않는다. 서비스가 정상 발급하고 검증한 JWT의 sub·user도 발급 계약을 따른다.
- 같은 조건을 다시 검사하려면 다른 진입 경로, 전달 중 값 변경, 별도 업무 조건 등 기존 보장이 적용되지 않는 구체적인 이유가 있어야 한다. 가변 상태의 현재 권한·존재 여부 같은 업무 판단은 값의 형식 검증과 구분한다.
- 타입·entity를 만들었다는 이유로 생성자 검증이나 새 불변 조건을 추가하지 않는다. 의미 구분·저장·전달만 담당하는 타입은 그 책임을 유지한다.
- 형식·범위·길이 제한과 오류 경로는 요구사항·기존 계약·구체적인 실패 근거가 있을 때만 추가한다. 사용에 필요한 타입 변환에 별도 정책 검증을 덧붙이지 않는다.
- 요구사항을 만족하는 데 필요한 범위만 수정한다.
- 증상을 우회하지 말고 확인된 근본 원인을 수정한다.
- 같은 전제에 기반한 수정이 반복해서 실패하면 추가 수정 전에 그 전제를 확인한다.
- 구현하거나 수정한 부분을 실제로 실행해 검증한다. 실행할 수 없으면 그 이유와 미검증 범위를 보고한다.
- 도움이 될 것이라는 가정만으로 코드를 추가하지 않는다. 확인된 요구사항과 검증된 동작에 필요한 코드만 남긴다.
- 경계와 테스터빌리티를 감안하여 구현한다.
