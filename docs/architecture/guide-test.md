# 테스트·검증 가이드

테스트는 요구사항과 계약에 따른 동작이 깨졌을 때 실패하도록 구성한다.

- 테스트할 계약과 기대 결과를 먼저 정하고, 호출자가 사용하는 함수·API·CLI·UI 등 적절한 인터페이스를 통해 검증한다. 현재 구현의 결과를 그대로 기대값으로 삼지 않는다.
- 반환값, 오류, 공개 상태와 의미 있는 부작용을 확인한다. 내부 구현만 바뀌고 계약이 유지되면 테스트도 유지되도록 한다.
- 내부 helper의 호출 순서·횟수나 중간 자료구조는 계약상 필요할 때만 확인한다. 세밀한 경계값이나 내부 수준 테스트는 실제 요구, 위험 또는 재현된 결함에 근거해 추가한다.
- 변경된 동작과 의도를 검증하는 데 필요한 테스트만 추가하거나 수정한다. 기존 테스트가 같은 동작과 실패 위험을 검증하면 재사용하거나 보완하고, 자명한 구현이나 같은 실패를 반복 확인하기 위해 테스트를 추가하지 않는다.
- 프로젝트의 기존 테스트 명령과 공통 환경을 우선 사용한다. 외부 의존성의 실제 동작이 계약에 중요하면 격리된 실제 환경에서 확인하고, mock 결과를 실제 연동 검증으로 보고하지 않는다.
- 테스트는 실행 순서에 의존하지 않도록 전역 상태·환경변수·파일 등 상태와 자원을 격리하고 사용한 자원을 정리한다. 비동기 처리는 고정된 대기 시간에 기대지 않고 준비 상태와 완료 조건을 기한 내 확인한다.
- 검증 범위와 방법은 변경의 영향과 위험에 맞춘다. API 계약이나 호환성처럼 영향이 넓은 변경은 관련 호출부까지 확인하고, 문서 변경처럼 동작이 바뀌지 않는 경우에는 문서 내용과 링크를 확인한다. 테스트 수나 일률적인 커버리지 수치를 목표로 삼지 않는다.
- 실행한 명령·결과와 확인 범위를 기록하고, 실패·실행 오류·미실행을 구분한다.
- 동작을 바꾸는 경우 가능하면 실패하는 동작 중심 테스트를 먼저 작성하고, 최소 변경으로 통과시킨 뒤 변경 코드를 다시 검토한다. 선행 테스트가 비효율적이면 변경 위험에 맞는 다른 검증 방법을 선택하고 결과를 알린다.
- 테스트는 무엇을 보장하는지 쉽게 이해할 수 있어야 한다. 의도를 흐리거나 중복되는 장황한 테스트는 피한다.
