# HTTP·HTTPS 서버

| 관계 | 대상 | 설명 |

## 진행 상태와 현재 구성

- 요구사항: 승인. 사용자의 “설계 진행해”를 근거로 보완된 요구사항을 설계 기준으로 삼는다.
- 설계: 사용자의 “구현및 리뷰 진행” 요청에 따라 [PLN-HTTP](./plan.md) 채택.
- 구현·검증 / 자체 점검: 라이브러리 구현과 [검증·리뷰](./verification.md) 수행.
- [`tlab::http`](../../../tlab/src/http.rs)에 서버·정적 파일 설정과 실행 API를 제공한다. 앱은 기존 설정 로드와 tracing 초기화 상태를 유지한다. (확인)
- [`TlsCertFile`](../../../tlab/src/keyfiles/tls.rs)은 기존 인증서·개인키 로드와 개발용 조건부 생성을 이미 제공한다. 새 인증서 관리 기능을 중복 구현하지 않는다. (확인)
- 요구사항은 이 문서에, 공개 API와 실행·종료 계약은 [설계안](./plan.md)에 관리한다. 현재는 라이브러리 구현·리뷰 결과를 확인할 수 있다. (확인)

## 목적과 범위

다음은 사용자가 지정한 방향이다. (확인)

- Axum을 기반으로 `tlab::http` 기능을 제공하고 공개 진입점은 `http.rs`로 둔다.
- 단일 서버 구현체를 사용하고 상위가 HTTP·HTTPS 인스턴스를 설정에 따라 생성한다. 하나의 조립된 Router를 각 인스턴스에 전달한다. (확인: 후속 사용자 요청)
- HTTPS는 기존 TLS 인증서 파일 설정과 연계한다.
- 서버를 재시작하지 않고 실행 중 TLS 인증서·개인키를 변경할 수 있어야 한다. 초기 파일 로드만으로 범위를 한정하지 않는다. (확인)
- TLS 변경은 함수 형태로 제공하고 호출 시점·트리거·제어 방식은 앱이 결정한다. 파일 감시·주기 실행·관리 엔드포인트는 라이브러리에 추가하지 않는다. (확인)
- 정적 파일 제공도 설정으로 구성할 수 있게 한다.
- 정적 파일 설정은 HTTP·HTTPS와 함께 서버 설정 아래에 둔다. (확인)
- 업무 라우트·상태·미들웨어는 상위에서 조립하고 HTTP 기능에 전달한다.
- 공개 작업 API의 오류는 `tlab::Result`(`crate::Result`)로 처리한다.

이번 구현 범위는 라이브러리의 서버 실행과 정적 파일 연계다. 실제 앱의 업무 API·인증·JWT·gRPC 연결과 앱 기동 변경은 포함하지 않는다. (확인)

## 책임 구분

| 대상 | 책임 |
| --- | --- |
| 상위 앱 | 설정 집합·활성 인스턴스 선택, 공통 Router 조립, 모든 서버 준비·실행·실패·종료 조정, TLS 재로드 호출 시점 결정 |
| `http.rs` | 단일 리스너 준비·실행·종료, 선택적 TLS·재로드, 독립된 정적 Router 생성 |
| `keyfiles` | 인증서·개인키 로드·검증과 명시적인 개발용 생성 |

공개 API·소유권·호출 순서와 동작 정책은 [PLN-HTTP](./plan.md)에 정리한다. 이 문서에서는 구현 방식과 요구사항을 중복 관리하지 않는다. (추론)

## 앱 설정 예시

소비자가 앱 소유의 집합 설정에 `http: Option<http::Config>`, `https: Option<http::Config>`, `static_files: Option<http::StaticFilesConfig>`를 포함하는 예시다.
`http::Config`는 리스너 하나의 `bind`, 선택적 `tls`, 종료 기한만 가진다. `server`와 그 하위 HTTP·HTTPS 블록의 이름·선택·검증은 앱 책임이다. (확인·결정)

```toml
[server.http]
bind = "127.0.0.1:8080"

[server.https]
bind = "127.0.0.1:8443"

[server.https.tls]
certificate_chain = "./certs/server-chain.pem"
private_key = "./certs/server-key.pem"
# 개발 편의로 생성할 때만 명시한다. 기본값은 false다.
# generate_if_missing = true

[server.static_files]
prefix = "/static"
directory = "./public"
```

- 앱 집합 설정에서 `http`, `https` 블록 유무로 인스턴스를 활성화한다. 둘 다 없으면 앱이 잘못된 실행 설정으로 처리한다.
- 단일 `http::Config`는 필수 `bind`와 선택적 `TlsCertFile`, 기본 30초의 `shutdown_timeout_secs`를 가진다. TLS가 없으면 HTTP, 있으면 HTTPS다.
- 위와 같이 블록 이름으로 전송 방식을 구분하는 앱은 HTTP 블록의 TLS 미설정과 HTTPS 블록의 TLS 필수를 검증한다.
- 정적 파일의 `prefix`, `directory`는 앱의 공통 `server.static_files`에 둔다. 라이브러리 단일 인스턴스 설정에 포함하지 않고, 앱이 한 번 Router에 병합한다.
- 별도 `enabled` 필드나 인증서 식별자 저장소를 추가하지 않는다. 상대 파일 경로는 준비 시 작업 디렉터리 기준으로 해석한다. (확인·결정)

## 요구사항과 완료 조건

보완된 요구사항은 사용자의 설계 진행 요청에 따라 설계 기준으로 삼는다. 아래 검증은 구현 후 확인할 조건이며, 실행 결과가 아니다. (확인)

<a id="req-http-001"></a>
### REQ-HTTP-001: HTTP·HTTPS의 독립 설정과 동일 라우터

- HTTP만, HTTPS만, 둘 다 활성화하는 구성을 지원한다.
- 상위가 하나의 최종 Router를 복제해 각 단일 서버에 전달한다. 라이브러리 내부에서 HTTP·HTTPS 쌍이나 다중 인스턴스를 관리하지 않는다. 각 인스턴스는 동일한 라우트·상태·미들웨어·정적 파일 구성을 사용한다.
- 둘 다 미설정인 경우의 실행 요청 거부는 상위 앱의 책임이다. 라이브러리는 전달받은 단일 서버 설정을 검증한다.
- 완료 조건: 동일한 테스트 라우트의 응답을 HTTP·HTTPS에서 확인하고, 각 단독 구성과 모두 비활성화된 구성을 검증한다.

<a id="req-http-002"></a>
### REQ-HTTP-002: 상위 라우터 조립

- 상위가 상태 주입까지 완료한 `axum::Router`를 전달한다. HTTP 기능은 업무 라우트나 인증 정책을 추가하지 않는다.
- Axum의 `Router<S>`는 아직 주입할 상태가 남아 있다는 의미이므로, 서버에 넘기는 대상은 `Router<()>`다. [Axum 공식 문서](https://docs.rs/axum/latest/axum/struct.Router.html)에서 확인했다. (확인)
- 정적 파일 보조 API는 설정으로 Router를 만들고 상위가 업무 Router와 병합한 뒤 서버에 전달한다. 구체적인 함수 배치는 [설계안](./plan.md)에 둔다. (추론)
- 완료 조건: 상위에서 조립한 상태 의존 핸들러·미들웨어가 두 전송에서 동일하게 동작하며 라이브러리가 업무 경로를 추가하지 않는다.

<a id="req-http-003"></a>
### REQ-HTTP-003: TLS 파일 설정과 초기 준비

- HTTPS 설정에 `TlsCertFile`을 직접 포함하고 `load()`로 얻은 자료를 TLS 서버 설정에 사용한다.
- 기존 파일을 기본으로 사용한다. 개발용 생성은 기존 키파일 설정의 명시적 옵션을 따른다.
- 로드·키 불일치·TLS 설정 오류를 서버 준비 실패로 반환한다. 인증서 내용을 로그에 출력하지 않는다.
- 실행 중 TLS 교체는 REQ-HTTP-007에 포함한다. CA 발급·자동 갱신, mTLS, HTTP에서 HTTPS로의 자동 리다이렉트는 이번 기본 범위에 넣지 않는다. 외부에서 갱신한 인증서를 적용하는 것과 인증서를 발급·갱신하는 것은 구분한다.
- 완료 조건: 준비한 인증서로 실제 HTTPS 연결에 성공하고, 손상·불일치·누락 시 준비가 실패하며 기존 파일은 유지된다.

<a id="req-http-004"></a>
### REQ-HTTP-004: 설정에 따른 정적 파일 제공

- 선택적으로 지정한 URL 접두사에 지정 디렉터리를 연결한다. 첫 범위는 단일 접두사·디렉터리다.
- 설정은 `server.static_files`에 두고 HTTP·HTTPS 양쪽의 공통 라우터에 적용한다. 서버 설정 바깥에 별도의 정적 파일 설정을 요구하지 않는다.
- 기본 접두사는 `/static`이며, 해당 서비스 밖의 업무 라우트·fallback을 변경하지 않는다.
- 존재하지 않는 파일은 404로 처리하고 디렉터리 목록·자동 SPA fallback은 제공하지 않는다.
- 잘못된 접두사, 존재하지 않거나 디렉터리가 아닌 문서 루트는 준비 오류로 반환한다.
- 경로 이탈 요청 차단을 확인한다. 심볼릭 링크를 통한 외부 파일 접근의 허용·차단 범위는 서비스 선택과 함께 설계에서 명시한다.
- 완료 조건: 파일 응답·미존재 404·기존 API 유지·미설정 시 비활성화·잘못된 설정의 오류를 확인한다. 같은 정적 파일이 HTTP·HTTPS에서 응답해야 한다.

<a id="req-http-005"></a>
### REQ-HTTP-005: 준비 실패와 종료

- 상위가 활성화된 모든 서버의 `bind()`를 완료한 뒤 요청 처리를 시작한다. 중간 준비 실패 시 상위가 앞서 준비한 `Server`를 drop한다. 각 인스턴스는 자신의 리스너를 정리한다.
- 종료 요청은 상위가 전달하고 라이브러리는 프로세스 전역 신호 처리기를 설치하지 않는다.
- 인스턴스의 비정상 종료는 해당 `serve()` 호출자에게 전달한다. 다른 인스턴스를 함께 종료할지와 그 방법은 상위 정책이며, 이번 조립 예시는 `try_join!` 실패 시 나머지 실행 future를 drop한다. 라이브러리는 다른 인스턴스에 접근하지 않는다. (확인: 사용자 요청에 따른 책임 변경)
- 정상 종료 시 새 연결을 중단하고 진행 중 요청을 정리한다. 종료 대기 한도와 구체 API는 설계에서 결정한다. 후속 사용자 지시에 따라 미완료 TLS 핸드셰이크는 백엔드 timeout을 따르며 종료 기한 안의 즉시 취소는 보장하지 않는다. 즉시 연결 차단과 외부 트래픽 드레이닝은 상위 인프라 책임이다. (확인)
- 완료 조건: 상위의 준비 순서에서 포트 충돌·TLS 오류 시 부분 기동이 남지 않고, 각각 전달한 종료 요청으로 서버가 종료되며 실행 오류가 호출자에게 전달된다. 상위 `try_join!` 실패 시 다른 인스턴스 취소를 검증한다.

<a id="req-http-006"></a>
### REQ-HTTP-006: 공통 Result 사용

- 공개 서버 실행 함수와 TLS 재로드 작업은 `crate::Result<()>`, 정적 파일 연결 보조 함수는 `crate::Result<axum::Router>`로 반환한다. 실행 중 제어를 위한 준비 함수·핸들을 추가한다면 이 API도 `crate::Result`로 반환한다.
- 잘못된 설정과 준비·실행 오류는 기존 `tlab::Error`로 전달하며, 하위 라이브러리 오류를 공개 반환 타입에 직접 노출하지 않는다. 문맥과 원인 보존 방식은 기존 에러 계약을 따른다.
- HTTP 요청의 404 등은 응답 상태다. 업무 핸들러의 오류를 어떤 HTTP 응답으로 매핑할지는 상위 라우터의 책임이며, 이번에 `tlab::Error` 전체의 전역 응답 변환 정책을 추가하지 않는다.
- 완료 조건: 공개 API의 반환 타입과 실패 원인 전달을 확인한다. 내부 진단 내용이 HTTP 응답으로 자동 노출되지 않아야 한다.

<a id="req-http-007"></a>
### REQ-HTTP-007: 실행 중 TLS 변경

- HTTPS를 실행한 상태에서 인증서·개인키 파일의 변경 내용을 재로드하고, 서버 재시작 없이 TLS 설정을 교체할 수 있어야 한다. (확인)
- 앱이 호출할 수 있는 TLS 변경 함수를 제공한다. 호출 시점과 파일 감시·스케줄·관리 API 등의 제어 수단은 앱에서 결정하고, 라이브러리는 이를 구현하거나 자동 등록하지 않는다. (확인)
- 실행 중 서버의 TLS 대상에 함수를 어떻게 연결하고 어떤 입력으로 재로드할지는 설계에서 정한다. 특정 앱 제어 방식이나 별도 제어 프레임워크를 공개 계약으로 요구하지 않는다.
- 첫 범위는 해당 인스턴스의 `tls`에 지정된 동일한 경로의 파일 내용 변경이다. 파일 경로·바인딩 주소·라우터의 실행 중 변경은 별도 범위다.
- 재로드는 인증서·개인키를 모두 읽고 기존 키파일 계약에 따라 검증한 뒤 성공한 자료만 한 번에 활성화한다. 파일 누락·부분 교체·키 불일치·읽기 실패·TLS 설정 실패 시 기존 활성 설정을 유지하고 `tlab::Result`로 오류를 반환한다.
- 실행 중 재로드에서는 개발용 생성 옵션이 활성화되어 있어도 파일을 생성하거나 교체하지 않는다. 새 자료를 읽지 못한 경우 기존 설정을 유지하기 위한 정책이다.
- 새 TLS 설정은 교체 후 시작하는 핸드셰이크에 적용하고, 이미 진행 중인 연결은 강제로 끊지 않는다. 핸드셰이크와 설정 교체의 정확한 적용 경계는 선택한 서버 라이브러리에 맞춰 설계에서 명시한다.
- HTTP 리스너·업무 라우터·정적 파일 구성에는 영향을 주지 않는다. HTTPS가 미설정인 경우 재로드 작업은 명확한 오류로 반환한다.
- 완료 조건: 서버를 실행한 채 A 인증서로 연결한 후 파일을 B로 교체하고 재로드하여 새 연결이 B를 제시하는지 확인한다. 실패한 재로드 후에는 A 또는 마지막으로 성공한 설정이 계속 사용되어야 한다. 기존 연결 유지와 HTTP 정상 응답도 확인한다.

## 작성 기록

- 사용자의 Axum·HTTP/HTTPS 분리·같은 라우터·TLS 파일·정적 파일·상위 라우터 조립·`http.rs` 요청을 반영했다.
- 추가 지시인 `tlab::Result` 반환 계약을 요구사항에 반영했다.
- 사용자 의견에 따라 정적 파일 설정을 서버 설정 아래 `static_files`로 이동했다. HTTP·HTTPS의 공통 설정으로 두며 실제 연결 API는 설계 단계에서 확정한다.
- 사용자 의견에 따라 초기 TLS 파일 연계뿐 아니라 실행 중 TLS 변경을 필수 범위에 추가했다. 실패 시 기존 활성 설정을 보존하는 재로드 정책과 검증 조건을 제안으로 정리했다.
- 사용자 확인에 따라 TLS 변경은 함수로만 제공하고, 호출 제어는 앱에서 정하도록 범위를 확정했다. 파일 자동 감시 등 라이브러리의 제어 기능 도입 여부는 미결정 사항에서 제거했다.
- 현재는 문서 초안만 작성했다. 의존성·코드·앱 설정은 변경하지 않았다. (확인)
- 재설계 요청에 따라 중복된 설계·전달 사항을 정리하고 상세 설계와 기존 구현·변경 기록은 [PLN-HTTP](./plan.md)로 옮겼다. 요구사항 ID와 사용자가 지정한 범위는 유지했다. (확인)
- 사용자의 구현·리뷰 요청으로 설계를 채택하고 라이브러리를 구현했다. 후속 의견에 따라 별도 TLS accept 취소를 제거하고 종료·인프라 책임을 REQ-HTTP-005에 반영했다. [구현 기록](./plan.md#구현변경-기록)과 [검증·리뷰](./verification.md)에 결과를 남긴다. (확인)
- 단일 서버 구현체·상위 HTTP/HTTPS 인스턴스 관리 제안과 “반영해줘” 요청에 따라 설정 집합과 다중 서버 정책을 상위 책임으로 이동했다. 요구사항의 사용자 목표는 유지하고 구현 경계 변경을 REQ-HTTP-001·005와 설계에 반영했다. (확인)
