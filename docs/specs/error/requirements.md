# tlab 공통 에러 요구사항

## 연결 문서

| 관계 | 대상 | 설명 |
| --- | --- | --- |

프로젝트 역할과 현재 구조는 [아키텍처](../../architecture/index.md), [크레이트 설정](../../../tlab/Cargo.toml), [라이브러리 진입점](../../../tlab/src/lib.rs)을 참조한다. 이 요구사항을 실현하는 설계 문서에서 `realizes` 관계를 관리한다. (확인)

## 목적·사용 방식·범위

- 대상 사용자는 `tlab`과 이를 사용하는 Rust 애플리케이션의 개발자다. 공통 에러와 반환 타입으로 오류 생성·변환·전파를 일관되게 처리한다. (추론)
- `thiserror` 기반 enum을 `error.rs`에 정의하고, `Internal(anyhow::Error)`, `Cow<'static, str>` 메시지, 외부 에러 변환, `pub type Result<R>`을 제공한다. 사용자가 지정한 기술 제약이다. (확인)
- 개발자는 공통 에러를 생성하거나 외부 에러를 변환하여 반환하고, 호출자는 에러 종류와 메시지·원인을 확인한다. (추론)
- 이번에는 공통 계약을 정의한다. 에러 종류는 실제 작업에서 필요해질 때 확장하며, DB는 특정 라이브러리를 선택하지 않고 변환 계약만 정의한다. (확인)
- 구현·의존성 추가·기존 코드 변경, DB 기능 구현, HTTP 상태 코드 매핑, 로깅·사용자 화면의 에러 노출 정책은 이번 산출물의 범위에서 제외한다. (추론)

## 사용 시나리오

| 시나리오 | 상황·계기 | 사용자 행동과 시스템 반응 | 기대 결과 |
| --- | --- | --- | --- |
| S1: 일반 에러 반환 | 작업을 수행할 수 없는 상태 | 개발자가 상태 설명을 담은 에러를 생성하여 반환 | 호출자가 종류와 메시지를 확인 |
| S2: 외부 에러 전파 | 파일 작업 등에서 오류 발생 | 외부 에러를 공통 에러로 변환하거나 `?`로 전파 | 호출자가 공통 타입으로 처리하고 원인 확인 |
| S3: 미분류 에러 반환 | 전용 종류가 없는 오류 발생 | `anyhow::Error`를 `Internal`로 변환하여 반환 | 새로운 종류 없이 오류를 전파하고 원인 확인 |
| S4: 에러 확장 | 후속 작업에서 별도 분기가 필요 | 필요한 종류와 변환을 추가 | 같은 공통 에러·Result 계약 안에서 처리 |

시나리오는 사용자 요청을 구체화한 사용 흐름이다. (추론)

## 세부 기능

| 기능 | 책임·입력·결과 | 관련 시나리오 | 공통 기능·의존 관계 |
| --- | --- | --- | --- |
| 공통 에러 정의 | 에러 종류와 부가 정보를 enum으로 표현 | S1–S4 | `thiserror`, `error.rs` |
| 메시지 표현 | 정적 문자열 또는 실행 중 생성한 문자열을 소유권에 맞게 보관 | S1 | `Cow<'static, str>` |
| 외부 에러 변환 | 지원하는 외부 에러를 공통 타입으로 변환하고 원인 보존 | S2, S4 | I/O 변환, 향후 DB 변환 |
| 미분류 에러 수용 | `anyhow::Error`를 `Internal`에 보관 | S3 | `anyhow` |
| Result 공개 | 성공 타입만 지정하는 공통 반환 타입 제공 | S1–S4 | 공통 에러 타입 |

기능 구성은 명시된 요구를 사용 흐름에 연결한 것이다. (추론)

## 요구사항과 검증 조건

아래 요구사항의 우선순위는 모두 필수다. DB의 구체적인 변환 구현과 추가 에러 종류는 후속 작업에서 확정한다. (확인)

<a id="req-error-001"></a>
### REQ-ERROR-001: 공통 에러 타입과 모듈

- `tlab/src/error.rs`에 `thiserror` 기반 공개 enum을 정의한다. (확인)
- 타입 이름은 `Error`, 기본 접근 경로는 `tlab::error::Error`와 `tlab::Error`로 제안한다. 이는 호출 편의를 위한 공개 경로이며 사용자 지정 이름은 아니다. (추론)
- 관련 시나리오·기능: S1–S4, 공통 에러 정의.
- 검증 조건: 외부 사용 코드에서 공개 경로로 에러를 참조하고 종류별로 분기할 수 있다. 에러가 `std::error::Error`, `Display`, `Debug` 계약을 충족한다. (추론)
- 합의 상태·근거: 모듈·enum·`thiserror`는 사용자 명시 요구, 이름·재노출 경로는 제안.

<a id="req-error-002"></a>
### REQ-ERROR-002: 메시지를 포함하는 일반 에러

- 일반 에러는 `Cow<'static, str>`를 가져 에러 메시지를 포함한다. 사용자 예시인 `IllegalState(Cow<'static, str>)`를 최초 일반 에러로 제안한다. (확인: 타입 제약·예시 / 추론: 최초 종류로 채택하는 제안)
- 정적 메시지와 실행 중 생성한 `String` 메시지를 모두 표현할 수 있어야 한다. 정적 문자열에 대해 소유 문자열 생성을 강제하지 않는다. (추론)
- `Display`로 오류 설명을 확인할 수 있어야 한다. 정확한 접두사·문장 형식은 설계에서 정한다. (추론)
- 관련 시나리오·기능: S1, 메시지 표현.
- 검증 조건: `Cow::Borrowed`와 `Cow::Owned`로 각각 생성한 에러가 메시지를 유지하며, 생성 함수의 지역 `String`에서 소유권을 넘긴 메시지도 반환 후 유효하다. (추론)
- 합의 상태·근거: `Cow` 메시지는 사용자 명시 요구. `IllegalState`의 최초 포함과 표시 정책은 제안.

<a id="req-error-003"></a>
### REQ-ERROR-003: 미분류 에러 수용

- `Internal(anyhow::Error)`로 전용 종류가 정의되지 않은 에러를 수용한다. (확인)
- `anyhow::Error`에서 공통 에러로 변환할 수 있어야 한다. 이미 지원하는 외부 에러 변환은 해당 분류를 유지한다. 미분류 원본을 직접 `?`로 전파하는 범용 변환까지 요구하는 것은 아니며, 필요한 경우 먼저 `anyhow::Error`로 감싼다. (추론)
- 원본 에러와 추가된 문맥을 문자열로만 치환하여 잃지 않도록 한다. (추론)
- 관련 시나리오·기능: S3, 미분류 에러 수용.
- 검증 조건: `anyhow::Error` 변환 결과가 `Internal`이며, 보관한 값에서 문맥과 원인 체인을 확인할 수 있다. (추론)
- 합의 상태·근거: `Internal`과 페이로드는 사용자 명시 요구. 변환 방식·원인 보존은 요청 취지를 구체화한 제안.

<a id="req-error-004"></a>
### REQ-ERROR-004: 외부 에러 변환과 원인 보존

- `IoError`, `DbError` 등 외부 에러를 공통 에러로 변환하여 일관되게 처리하는 계약을 제공한다. DB는 이번에 변환 계약만 정의한다. (확인)
- I/O의 최초 구체 대상은 `std::io::Error`로 제안한다. `From<std::io::Error>`를 통해 명시적 변환과 `?` 전파를 지원하고, 변환 결과를 I/O 에러로 식별할 수 있게 한다. (추론)
- DB 라이브러리가 선정되는 후속 작업에서 해당 에러 타입의 변환을 제공한다. 변환 결과는 DB 에러로 식별할 수 있어야 하며, 원본 원인을 유지해야 한다. 지금은 `DbError`의 페이로드나 특정 DB 의존성을 확정하지 않는다. (확인: 계약만 정의 / 추론: 세부 계약)
- 원본 외부 에러는 문자열로만 저장하지 않는다. 보관한 원본과 `std::error::Error::source()`를 통해 원인을 조사할 수 있게 한다. 외부 에러에 별도 `Cow` 메시지 필드를 일괄 요구하지 않는 것으로 해석한다. (추론)
- 관련 시나리오·기능: S2, S4, 외부 에러 변환.
- 검증 조건: `std::io::Error`의 명시적 변환과 `?` 전파가 같은 I/O 분류로 귀결되며, 원본의 종류와 메시지를 확인할 수 있다. 향후 DB 변환도 같은 기준으로 분류·원인 보존을 확인한다. (추론)
- 합의 상태·근거: 외부 변환과 DB 계약 범위는 사용자 명시 요구. I/O 대상·원인 보존·`Cow` 적용 범위는 제안.

<a id="req-error-005"></a>
### REQ-ERROR-005: 공통 Result 타입 공개

- `pub type Result<R>`로 공통 에러를 사용하는 반환 타입을 공개한다. (확인)
- 의미는 `std::result::Result<R, Error>`이며, `tlab::error::Result<R>`와 `tlab::Result<R>`로 사용할 수 있게 제안한다. 두 번째 에러 타입 매개변수는 이번 요구에 포함하지 않는다. (추론)
- 관련 시나리오·기능: S1–S4, Result 공개.
- 검증 조건: 외부 사용 코드가 `tlab::Result<R>`로 성공값과 공통 에러를 반환하고, 지원하는 외부 에러를 `?`로 전파할 수 있다. (추론)
- 합의 상태·근거: 단일 성공 타입 매개변수의 별칭은 사용자 명시 요구. 구체적인 재노출 경로는 제안.

<a id="req-error-006"></a>
### REQ-ERROR-006: 필요에 따른 에러 확장

- 기본 에러를 먼저 제공하고, 작업 중 실제 필요가 생길 때 종류와 변환을 확장한다. 예상 가능한 모든 에러를 미리 나열하지 않는다. (확인)
- 추가 종류는 기존 종류나 `Internal`과 구분하여 처리할 실제 필요를 근거로 정한다. 외부 에러가 추가되면 분류와 원인 보존 계약을 함께 정의한다. (추론)
- 공개 enum에 종류를 추가할 때 소비자의 패턴 매칭에 미치는 호환성 영향을 검토한다. `#[non_exhaustive]` 등 구체적인 확장 정책은 설계에서 결정한다. (추론)
- 관련 시나리오·기능: S4, 공통 에러 정의·외부 에러 변환.
- 검증 조건: 최초 범위에 근거 없는 추가 종류·DB 의존성이 없고, 후속 추가 시 공개 API 호환성과 해당 변환 계약의 검증 근거가 있다. (추론)
- 합의 상태·근거: 점진적 확장은 사용자의 후속 명시 요구. 추가 판단 기준·호환성 검토는 제안.

## 선택 기준과 결정 범위

- 선택 우선순위는 명시 요구 충족, 원인 보존, 호출부의 사용 편의, 최소한의 종류·의존성 순으로 제안한다. (추론)
- AI는 요구된 타입·메시지·변환 의미를 유지하는 범위에서 표시 문구, 도출 속성, 작은 보조 API 등 설계 세부사항을 정할 수 있다. 외부 크레이트의 구체적인 버전은 구현 시 확인한다. (추론)
- DB 라이브러리 도입, 일반 에러 종류의 대량 추가, 에러를 외부 응답에 노출하는 정책은 이번 계약 정의에서 확정하지 않는다. 실제 필요와 후속 작업 범위를 확인하여 결정한다. (확인: DB·점진적 확장 / 추론: 노출 정책 경계)

## 검토와 변경 기록

- 사용자 후속 답변에 따라 DB는 계약 정의만 포함하고, 에러 종류는 작업 중 확장하도록 범위를 명확히 했다. (확인)
- `Cow`는 일반 에러의 메시지 요구로 해석했다. 원본을 보존해야 하는 외부 에러·`Internal`에 별도 메시지를 중복 요구하지 않기 위한 제안이다. (추론)
- 빈 문자열·다국어 메시지에 별도의 검증·변환 정책은 요구하지 않는다. 이 공통 타입의 계약에는 권한 판단, 재시도, 로깅 실행을 포함하지 않는다. (추론)
- 지원하는 외부 에러는 전용 분류로 변환하고, 전용 종류가 없는 경우 `Internal`을 사용하는 것으로 역할을 구분했다. 이는 모든 외부 에러를 자동으로 포괄하는 변환 구현을 요구하지 않는다. (추론)
- 기존 아키텍처 문서의 작업 중 변경은 유지하며, 이번 산출물은 이 요구사항 문서 하나다. (확인)
- 후속 `create-plan` 요청에 따라 최초 종류·메시지 범위·확장 호환성의 설계 제안을 연결했다. 요구사항이나 설계의 채택 상태를 변경한 것은 아니다. (확인)

## 구현계획에 전달할 내용

- 최초 구현 대상 제안: 공통 `Error`와 `Result`, `IllegalState`의 `Cow` 메시지, `Internal(anyhow::Error)`, I/O 변환·원인 보존, 공개 경로. DB는 계약을 전달하고 구현은 DB 도입 시 연결한다. (추론)
- 충족 여부는 REQ-ERROR-001–006의 공개 사용 경로, 반환값·종류·메시지·원인 관찰로 판단한다. 이 문서는 검증 조건을 정의하며 구현 검증을 실행한 기록은 아니다. (확인)
- 요구사항 정의를 완료하고, [설계안](./plan.md)에서 공개 경로·최초 일반 에러·확장 호환성 정책을 구체화했다. 사용자의 후속 구현 요청으로 이번 요구사항·설계안을 구현 기준으로 채택했다. 최초 공통 에러 구현과 검증 결과는 설계 문서의 구현·변경 기록에 남긴다. DB의 구체 변환은 계속 보류한다. (확인)
