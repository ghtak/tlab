## 현재 설계와 범위

사용자의 타입 분리, 알고리즘별 검증, 라이브러리 위임, 비용 상한 제거 및 불필요한 함수 제거 요청을 반영한 현재 설계다. 이전 제안과 검증 결과는 하단의 구현·변경 기록에 보존한다. (확인)

`tlab::password`는 `PasswordHasher: Send + Sync` trait을 제공한다. `argon2id::{Config, Hasher}`와 `pbkdf2_sha256::{Config, Hasher}`가 각각 자신의 설정·생성·검증을 담당한다. 앱은 사용할 구현체와 설정 조합을 결정한다. 현재 앱에는 사용처가 없으며 계정 저장·로그인·데이터 이전은 범위 밖이다. (확인)

```rust
pub trait PasswordHasher: Send + Sync {
    fn hash(&self, password: &str) -> tlab::Result<String>;
    fn verify(&self, password: &str, encoded_hash: &str) -> tlab::Result<bool>;
}
```

각 구현체의 `Hasher::new(&Config)`는 설정을 검증하고 생성 매개변수를 소유한다. 설정은 `Default`, `Deserialize`, `Clone`, `Debug`를 제공하며 알 수 없는 필드를 거부한다. 설정 로더에 조합할 수 있고 공통 알고리즘 선택 enum은 두지 않는다. (확인)

| 구현체 | 기본 설정 | 생성 제약 |
| --- | --- | --- |
| Argon2id | memory_kib 19,456, iterations 2, parallelism 1 | memory_kib ≥ 19,456, iterations ≥ 2 및 `argon2::Params` 유효성 조건 |
| PBKDF2-SHA256 | iterations 600,000 | iterations ≥ 600,000 |

출력은 32바이트로 고정하고 OS 난수에서 16바이트 salt를 생성한다. 비밀번호의 UTF-8 바이트를 그대로 사용한다. 저장 형식은 PHC이며 암호 연산·비교는 RustCrypto에 위임한다. 파서의 인코딩 salt 64자 제한을 따른다. 임의의 문자열 길이·salt·출력 길이 검사를 별도로 추가하지 않는다. (확인)

각 구현체는 자신의 알고리즘만 검증한다. Argon2id는 버전 19, PBKDF2-SHA256은 버전 필드 없는 형식만 허용한다. salt·digest·필수 매개변수 누락과 중복, PBKDF2 반복 0을 거부한다. 나머지 형식·매개변수 유효성은 라이브러리에 맡긴다. 같은 알고리즘의 생성 비용을 바꿔도 저장 해시의 비용으로 검증한다. 다른 알고리즘으로 전환한 경우 호출자가 이전 구현체를 선택해야 한다. 자동 재해시나 `needs_rehash`는 제공하지 않는다. (확인)

일치는 `Ok(true)`, 비밀번호 불일치는 `Ok(false)`, 설정·PHC 입력 오류는 `Error::InvalidInput`, 난수·인코딩·해시 생성 실패는 `Error::Internal`로 반환한다. 오류는 발생 상황을 설명하되 비밀번호나 해시 원문을 포함하지 않는다. 오류와 salt 처리용 별도 공통 함수는 두지 않는다. (확인)

## 호출 경계와 위험

사용자 요청에 따라 프로젝트 자체 연산 비용 상한은 없다. 검증 대상은 호출자가 관리하는 저장 해시이며, 외부에서 받은 임의의 PHC를 무제한으로 검증하는 API로 사용하면 자원 고갈이 가능하다. 저장소 보호와 실행 자원 관리는 호출자 책임이다. 동기 연산이므로 비동기 앱은 블로킹 실행과 동시성 제한을 구성한다. (확인·추론)

라이브러리는 DB·로그·전역 실행 자원을 소유하지 않는다. 앱에 신규 사용처나 저장 데이터를 추가하지 않아 저장소 내에서는 코드·의존성 복원으로 되돌릴 수 있다. 외부 소비자가 도입한 후의 복구는 해당 코드·저장 해시의 호환성을 별도로 판단한다. (확인·추론)

## 검증 기준

[요구사항 001](./spec.md#req-password-hash-001)과 [002](./spec.md#req-password-hash-002)는 각 구현체의 생성·정답·오답·서로 다른 salt·다른 알고리즘 거부 및 PBKDF2 벡터로 검증한다. [003](./spec.md#req-password-hash-003)은 설정 로더·기본값·알 수 없는 필드·최소 비용·기존 상한 초과 설정 수용으로 검증한다. [004](./spec.md#req-password-hash-004)는 잘못된 PHC·누락·중복·지원하지 않는 알고리즘·버전과 오류 메시지 비밀 미노출로 검증한다. (확인)

## 구현·변경 기록

- 요구사항 승인 후 설계를 작성하고 사용자의 구현·리뷰 요청으로 승인받았다. (확인)
- PHC 파서의 salt 입력 제한보다 긴 salt는 별도로 디코딩하고 나머지 PHC를 검증한 뒤 RustCrypto의 원시 연산과 상수 시간 비교를 사용한다. 승인된 salt 범위와 알고리즘 계약을 유지하기 위한 구현 세부사항이다. (확인)

### 변경 제안: 알고리즘별 구현체와 설정 분리

- 계기: 사용자가 Hasher와 Config를 각각 개별 구현 타입으로 두는 방향을 제안했다. 기존 설계의 enum 기반 단일 `Config`와 `Hasher`는 구현되어 있으나, 사용자의 “반영해” 응답으로 이 변경을 승인받았다. (확인)
- 제안: `password::argon2id::{Config, Hasher}`와 `password::pbkdf2_sha256::{Config, Hasher}`를 제공하고 두 `Hasher`가 기존 `PasswordHasher` trait을 구현한다. 설정과 생성 검증은 각 구현체가 담당한다. 알고리즘 선택과 인스턴스 조립은 호출자에게 맡기며, 공통 enum `Config`와 `Hasher`는 제거한다. (추론)

```rust
use tlab::password::{self, PasswordHasher};

let argon = password::argon2id::Hasher::new(&argon_config)?;
let pbkdf = password::pbkdf2_sha256::Hasher::new(&pbkdf_config)?;
let hasher: &dyn PasswordHasher = &argon;
let encoded = hasher.hash("password")?;
# Ok::<(), tlab::Error>(())
```

- 두 `Config`는 각 모듈의 구조체이고 기존 알고리즘별 필드·기본값·허용 범위와 `Deserialize`, 미지정 필드 기본값·알 수 없는 필드 거부를 유지한다. 설정에서 알고리즘을 선택해야 하는 앱은 자체 enum 또는 구성 방식으로 조합한다. 기존 YAML의 `algorithm` 태그를 포함한 공통 설정 형식과 공개 타입은 사라지므로 호출자의 설정·코드 변경이 필요하다. 저장된 PHC의 형식은 변경하지 않는다. (추론)
- 승인된 교차 알고리즘 검증 계약을 유지하기 위해 양쪽 구현체의 `verify`는 PHC 알고리즘에 따라 두 형식을 모두 검증한다. 공통 검증 로직은 모듈 내부에서 공유하며 새 공개 검증 관리자나 전역 설정은 추가하지 않는다. 따라서 구현체의 이름은 생성 알고리즘을 뜻하며 검증 가능 알고리즘을 제한하지 않는다. (추론: 기존 계약 유지 제안)
- 장점은 생성 시 무관한 알고리즘 분기가 사라지고 설정과 구현 책임이 함께 놓이는 점이다. 반면 두 구현체가 다른 알고리즘의 해시도 검증하는 점은 타입 이름만으로 드러나지 않으므로 공개 API 문서에 명시한다. 알고리즘별로 자기 해시만 검증하게 바꾸는 대안은 기존 저장 해시의 전환 동작을 바꾸므로 별도 계약 변경이 된다. (추론)
- 검증: 기존 생성·오답·교차 알고리즘·비용 제한·긴 salt 테스트를 두 구현체로 적용하고, 각 설정이 로더에 조합되며 오류·알 수 없는 필드를 거부하는지 확인한다. 필수 검사와 변경 대상 리뷰를 다시 수행한다. (추론)


### 변경: 연산 비용 상한 제거

- 사용자의 “상한도 굳이 검증할필요는 없을듯” 요청에 따라 생성 설정과 저장 해시의 Argon2 메모리·반복·병렬도 및 PBKDF2 반복 횟수에 두었던 프로젝트 자체 상한을 제거한다. 최소 생성 비용과 0·라이브러리가 거부하는 잘못된 조합 검증은 유지한다. PHC 문자열·salt·출력의 형식 길이 제한은 이 연산 비용 변경에 포함하지 않는다. (확인·추론)
- 검증 비용은 저장된 PHC 매개변수에 따른다. 공격자가 해시를 조작할 수 있으면 과도한 CPU·메모리 사용이나 프로세스 중단이 발생할 수 있다. 호출자가 해시 저장소를 보호하고 작업의 동시성·자원을 제어해야 한다. 이 모듈의 자체 비용 제한은 없다. (추론)
- 기존 상한 거부 테스트는 제거하고, 기존 상한을 초과한 유효 설정이 생성자에서 수용되는지 실제 고비용 연산 없이 확인한다. (추론)


### 변경: 알고리즘별 검증 책임

- 사용자의 “verify 를 호출하는 구조는 좀 아닌듯 저걸 굳이 다시 모을 필요가 없자나” 요청에 따라 이전 교차 알고리즘 검증 제안을 변경한다. 각 `Hasher`의 `verify`가 자신의 알고리즘만 처리하며, 다른 알고리즘의 해시는 `InvalidInput`을 반환한다. 공통 코드는 PHC 형식의 공통 파싱과 salt 처리만 맡고 알고리즘 선택·검증을 통합하지 않는다. (확인·추론)
- 알고리즘 전환 시 기존 해시를 검증하려면 호출자가 해당 알고리즘의 구현체를 선택해야 한다. 저장된 PHC의 형식과 각 알고리즘의 비용 해석은 유지한다. (추론)

### 추가 제안: RustCrypto의 PHC 검증 API 사용

- 사용자가 Argon2와 PBKDF2 각각에서 `PasswordHash::new`, 라이브러리의 `verify_password`, `needs_rehash`를 사용하는 간결한 구현을 제시했다. 현재 수동 PHC 정규화와 알고리즘별 검증은 이전의 디코딩된 salt 최대 64바이트 허용 계약 때문에 복잡해졌으며, 이 계약의 필요성은 확인되지 않았다. (확인·추론)
- 제안: 두 구현체에서 라이브러리의 PHC 파싱·검증을 직접 사용하고 수동 salt 정규화와 원시 해시 계산·비교를 제거한다. `password-hash` 0.5는 인코딩된 salt를 최대 64자로 제한하여 디코딩된 salt 49–64바이트의 기존 PHC는 거부하므로, 기존 지원 범위가 줄어든다. 생성한 16바이트 salt에는 영향이 없다. (확인)
- 라이브러리의 기본 검증은 PHC에 저장된 알고리즘을 따른다. Argon2id와 PBKDF2-SHA256만 검증하는 현재 계약은 각각 알고리즘·버전 확인을 추가해 유지한다. `verify`는 일치 여부 `Result<bool>`과 불일치·오류 구분을 유지하고, 제시된 `Result<()>` 전환 여부는 별도 결정으로 다룬다. (확인·추론)
- `needs_rehash`는 기존 trait에 없던 공개 기능이다. 새로 추가할 경우 비용이 현재 값보다 다르기만 해도 재해시할지, 더 강한 해시는 유지할지 등 정책이 필요하다. 생성 설정의 출력 길이도 현재 고정 32바이트이므로 예시의 설정 가능 `output_len`은 별도 계약 변경이다. (확인·추론)
- `SaltString::generate`는 난수 실패를 반환하지 않는 API이므로 난수 획득 실패를 오류로 전달하는 기존 계약을 유지하려면 현재의 fallible 난수 획득은 남긴다. (확인)
- 상태: 사용자의 “제안대로 구현해” 요청으로 승인·구현. 두 알고리즘 정상·불일치·다른 알고리즘·잘못된 PHC 테스트와 변경된 salt 경계, 필수 검사·리뷰를 다시 실행한다. (추론)
