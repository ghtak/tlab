# DB 연결·트랜잭션 접근 요구사항

## 연결 문서

| 관계 | 대상 | 설명 |
| --- | --- | --- |
| realizes | [REQ-ERROR](../error/requirements.md#req-error-004) | DB 도입 시 공통 에러 분류·변환·원인 보존 계약 |

분석 원문은 [백서](./whitepaper.md), 현재 구조는 [아키텍처](../../architecture/index.md)를 참조한다. 백서는 방향을 설명하는 초안이며, 코드 그대로의 채택을 요구하지 않는다. (확인)

## 단계별 진행 상태

- 요구사항 정리: 승인. SQLx·PostgreSQL을 최초 대상으로 제안한 뒤 사용자가 “설계 진행해”라고 요청한 것을 승인 근거로 한다. Oracle은 후속 범위다. (확인)
- 설계: 승인. 사용자 “구현및 코드리뷰까지 진행해” 요청을 근거로 한다. (확인)
- 구현·검증 / 자체 점검 / 정식 코드 리뷰: 완료. 위 요청은 구현·검증·리뷰와 필요한 수정을 함께 승인한 것으로 기록하며 중간 재승인을 요구하지 않았다. 실행·리뷰 근거는 [PLN-DATABASE](./plan.md#구현검증-결과)에 있다. (확인)
- 적용 판단: 전체 백서는 새 DB 모듈·공개 API·드라이버 연동·트랜잭션 정책을 도입한다. 기존 구조 내 국소 수정에 해당하지 않으므로 `small-change` 가이드에 따라 요구사항 정의를 보완한다. 범위 확정 후 책임·계약 설계가 필요하며, 약식 구현 대상으로 확정하지 않는다. (추론)
- 승인 범위: REQ-DATABASE-001–005와 최초 SQLx·PostgreSQL 범위. 요구사항 승인은 “설계 진행해”, 설계·구현·검증·리뷰 승인은 후속 “구현및 코드리뷰까지 진행해” 요청을 각각 근거로 한다. (확인)

## 최초 백서 분석과 설계 전 상태

| 구분 | 분석 결과 |
| --- | --- |
| 핵심 목적 | 저장소 함수가 `Context`를 받아 일반 연결과 트랜잭션에서 같은 쿼리 경로를 사용한다. (확인) |
| SQLx 방향 | `sqlxdb.rs`에 풀, 연결, 트랜잭션, 짧게 빌리는 실행 문맥을 제공하는 안이다. (확인) |
| 추상화 경계 | 쿼리는 SQLx API와 백엔드 타입을 사용한다. `Context`는 연결·트랜잭션의 진입점을 통일하며, 서로 다른 드라이버의 SQL·바인딩 API까지 통일하는 계층은 아니다. (추론) |
| Oracle 예시 | 별도 드라이버에서도 유사한 역할을 구성하는 확장 예시다. 이번 구현에 포함되는지는 미결정이다. (확인) |
| 현재 코드 | `tlab/src/lib.rs`는 설정·에러 모듈을 공개한다. DB 코드·호출자·검증 도구는 없고 `tlab/Cargo.toml`에도 SQLx·Oracle·Tokio 의존성이 없다. (확인) |
| 공통 오류 | 기존 합의는 DB 오류를 구분하고 원본을 보존하는 변환이다. 구체 타입·페이로드는 DB 도입 때 결정하도록 보류했다. (확인) |

### 초안에서 해소할 부분

- SQLx `Config` 정의가 없고 오류 매핑이 `map_error`, `sqlxdb::map_error`, `sqlxdb::postgres::map_error`로 혼재한다. 공개 오류 분류·변환 경로를 설계에서 정해야 한다. (확인)
- SQLx 백엔드는 제네릭이지만 사용 예는 PostgreSQL이다. 최초 지원 DB, 런타임·TLS와 Cargo feature 정책은 정의되어 있지 않다. 제네릭 타입만으로 모든 백엔드의 지원·검증을 약속할 수 없다. (확인: 원문 / 추론: 지원 범위)
- `PoolStatus`는 개별 조회값을 모으는 형태다. 동시 실행에서 하나의 시점에 대한 정확한 스냅샷인지, 관측용 수치인지를 정해야 한다. (추론)
- SQLx 예시는 가변 대여로 문맥과 트랜잭션의 접근을 제한한다. Oracle 예시는 `Arc`를 복제하고 `&self`로 문맥·트랜잭션을 만들므로 같은 연결에 여러 작업·루트 트랜잭션 핸들이 공존할 여지가 있다. 두 예시의 수명·배타성 계약은 같지 않다. (확인: 코드 형태 / 추론: 위험)
- Oracle 예시에는 미완료 트랜잭션의 `Drop` 처리 코드가 없고 savepoint 이름은 깊이에만 의존한다. 복제 가능한 문맥, 형제 savepoint, 외부 작업 취소 이후의 실행·반환 정책까지 별도 설계·검증이 필요하다. 드라이버 자체의 보장 여부는 확인하지 않았다. (확인: 코드 / 추론: 보완 필요)
- 백서 코드는 컴파일·실제 DB 실행 검증을 하지 않았다. 드라이버 버전별 API·trait 제약과 트랜잭션 동작은 설계 시 공식 문서·소스 및 실행으로 확인해야 한다. (확인)

## 목적·사용 방식·범위

대상은 `tlab`을 사용하는 Rust 애플리케이션 개발자다. 애플리케이션은 DB별 쿼리와 데이터 모델을 소유하고, `tlab`은 풀·연결·트랜잭션의 수명과 공통 오류 변환을 담당한다. 같은 저장소 함수를 일반 연결과 트랜잭션에서 재사용하는 것이 목표다. (추론: 백서에서 도출한 제안)

최초 범위는 SQLx·PostgreSQL이다. Oracle은 별도 후속 범위로 두고, 현재 범위에서는 Oracle 전용 코드나 두 드라이버를 묶는 공통 trait을 미리 도입하지 않는다. 최초 범위 제안 후 사용자의 설계 진행 요청으로 채택했다. (확인)

ORM, SQL 방언·바인딩 통일, 마이그레이션 도구, 자동 재시도, 업무별 저장소 구현은 이번 제안 범위에서 제외한다. 풀 상태 조회는 백서에 제시된 부가 기능으로 포함하되 지표·모니터링 시스템까지 확장하지 않는다. (추론: 범위 제안)

## 사용 시나리오

| 시나리오 | 사용자 행동과 시스템 반응 | 관찰할 결과 |
| --- | --- | --- |
| S1 일반 쿼리 | 설정으로 풀을 만들고 연결·문맥을 얻어 저장소 함수를 호출 | 트랜잭션 핸들 없이 SQLx 쿼리를 실행 |
| S2 트랜잭션 | 풀 또는 확보한 연결에서 시작하고 같은 저장소 함수를 호출한 뒤 commit 또는 rollback | commit한 변경은 남고 rollback한 변경은 남지 않음 |
| S3 중첩 작업 | 활성 트랜잭션 안에서 하위 트랜잭션을 시작하고 완료 | 하위 rollback은 하위 변경을 취소하고 외부 트랜잭션은 계속 사용 가능 |
| S4 실패·미완료 종료 | 연결·쿼리·트랜잭션 오류 또는 완료하지 않고 핸들 해제 | 공통 오류에서 원인 확인, 미완료 변경이 의도치 않게 확정되지 않음 |
| S5 상태 확인 | 연결을 새로 획득하지 않고 풀 상태 조회 | 설정된 최대 연결 수, 현재 크기·유휴 연결 수 확인 |

위 시나리오는 승인된 요구사항의 사용 흐름이다. 구체 API·검증 방법은 설계에서 정한다. (확인)

## 요구사항과 완료 조건

아래 필수 요구사항은 사용자의 설계 진행 요청으로 승인되었다. 지원 DB는 PostgreSQL이며 중첩 트랜잭션의 구체 API·수명 계약은 설계에서 정한다. (확인)

<a id="req-database-001"></a>
### REQ-DATABASE-001: 설정으로 연결 풀 사용

- URL과 최대 연결 수로 SQLx 풀을 초기화하고 연결을 획득한다. 설정 타입은 기존 설정 로더와 조합할 수 있어야 한다.
- 완료 조건: 선택한 DB에 정상 연결하고 쿼리를 실행한다. 잘못된 설정·연결 실패는 panic 대신 `tlab::Result`의 오류로 반환한다. 세부 입력 검증·풀 대기 정책은 설계에서 정한다.
- 관련 시나리오: S1, S4.

<a id="req-database-002"></a>
### REQ-DATABASE-002: 연결과 트랜잭션의 실행 문맥 통일

- 저장소 함수는 동일한 문맥 타입을 통해 일반 연결과 트랜잭션에서 SQLx 쿼리를 실행한다. SQL·바인딩·행 변환은 호출자가 소유한다.
- 완료 조건: 동일한 저장소 함수를 양쪽 경로에서 실행해 결과를 확인한다. 문맥이 원래 연결·트랜잭션 수명을 벗어나거나 활성 문맥과 충돌하는 완료 작업을 허용하지 않는지 확인한다.
- 관련 시나리오: S1, S2.

<a id="req-database-003"></a>
### REQ-DATABASE-003: 트랜잭션 경계와 미완료 처리

- 풀 또는 확보한 연결에서 트랜잭션을 시작하고 명시적으로 commit·rollback할 수 있다. 중첩 작업은 선택한 DB가 지원하는 savepoint 의미를 따른다.
- 완료 조건: commit·rollback 이후 저장된 값, 중첩 rollback 후 외부 작업의 지속과 최종 결과, 미완료 트랜잭션 해제 후 변경 미확정을 실행으로 확인한다. 완료한 핸들을 다시 사용하지 못하도록 한다.
- 관련 시나리오: S2, S3, S4. 취소·오류 후 연결 재사용 정책과 검증 경계는 설계에서 명시한다.

<a id="req-database-004"></a>
### REQ-DATABASE-004: DB 오류의 공통 변환과 원인 보존

- 초기화·연결·트랜잭션·쿼리에서 발생한 SQLx 오류를 DB 오류로 식별할 수 있도록 변환하고 원본 원인을 보존한다. 기존 I/O·설정·anyhow 변환 계약은 유지한다.
- 완료 조건: 명시 변환과 `?` 전파의 분류·원본 접근을 확인하고, 실제 쿼리 실패가 같은 계약을 따르는지 확인한다. SQL 상태 코드별 업무 오류 분류는 별도 요구가 없으므로 추가하지 않는다.
- 관련 시나리오: S4. 구체 enum 종류·페이로드·매핑 함수 공개 여부는 설계 사항이다.

<a id="req-database-005"></a>
### REQ-DATABASE-005: 풀 상태 조회

- 연결 획득 없이 최대 연결 수·풀 크기·유휴 연결 수를 조회할 수 있고, 상태를 직렬화할 수 있다.
- 완료 조건: 연결 획득·반환 전후 상태를 확인한다. 동시 갱신 중 수치 일관성의 보장 수준은 설계에서 명시하고, 여러 호출의 값을 하나의 원자적 스냅샷으로 보장하지 않는다.
- 관련 시나리오: S5.

## 선택 기준과 미결정 사항

우선순위는 트랜잭션 경계·원인 보존 → 기존 SQLx API 재사용 → 얇고 명확한 공개 표면 → 향후 다른 드라이버와의 역할 일관성이다. 구체 파일 구성·이름·최소 trait 제약은 설계에서 결정할 수 있으나 지원 DB·트랜잭션 정책·검증 범위를 임의로 확장하지 않는다. (추론: 제안)

| 항목 | 제안 또는 확인할 내용 | 영향·결정 시점 |
| --- | --- | --- |
| 최초 범위·지원 DB | SQLx·PostgreSQL로 승인, Oracle은 후속 | 설계 진행 요청을 근거로 해소 (확인) |
| 런타임·TLS·feature | Tokio·Rustls, SQLx 기본 feature 비활성화 | 설계 승인·구현 완료, TLS 실연동은 미검증 (확인) |
| 실제 DB 검증 | 기존 Compose·just 도구와 PostgreSQL 18.6 사용 | 호스트 Rust 드라이버·공개 API 통합 테스트 4개 통과 (확인) |
| 중첩 트랜잭션 | SQLx의 savepoint 처리 사용 | commit·rollback·Drop과 오류 후 외부 작업 지속 검증 완료 (확인) |

## 검토 기록과 다음 단계

- 원문은 수정하지 않고 분석·제안을 이 통합 문서에 정리했다. 기존 DB 작업 명세는 없으며 이 문서를 후속 단계에서도 보완한다. (확인)
- 최초 요구사항 정리에서는 문서만 작성했으며, 후속 승인으로 구현·검증·리뷰를 수행했다. 상세 실행 근거와 미확인 범위는 [설계 기록](./plan.md)에 남겼다. (확인)
- 사용자 “설계 진행해. 테스트 환경은 just db-up 로 가동상태야” 요청에 따라 요구사항을 채택하고 [설계](./plan.md)로 연결했다. 기존 통합 문서를 요구사항 기준으로 재사용하고, 정식 설계 산출물만 별도 연결한다. `small-change`의 단계별 승인 방식은 유지한다. (확인)
