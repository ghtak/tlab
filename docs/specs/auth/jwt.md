# JWT 기반 로그인 유지 기능 구상

## 목적과 범위

로그인 후 웹과 API에서 인증을 유지하고, Access Token 만료 시 Refresh Token으로 갱신한다. 토큰 발급·갱신·폐기는 직접 구현한다. Keycloak이나 OIDC 제공자 도입을 이번 범위의 전제로 두지 않는다. (확인: 대화 합의)

이 문서는 대화에서 합의한 기능·책임·정책과 로그인 식별 방식을 정리한다. DB 설계안은 [`0002_create_tlab_auth_refresh_token.sql`](../../../tlab-app/migrations/0002_create_tlab_auth_refresh_token.sql)에 작성하며, 구현 완료 여부를 나타내지 않는다. 미결정 사항이 있어 문서는 draft로 유지한다.

## 책임 구분

| 주체 | 책임 |
| --- | --- |
| 인증 기능 | 로그인 성공 후 토큰 발급, Refresh 저장·만료 확인·폐기, 갱신 시 최신 사용자·권한 정보 반영 |
| 웹·API 접점 | 공통 토큰 규칙을 사용하고 각 전달 방식에 맞게 요청·응답 처리 |
| 각 API 서비스 | Access JWT 검증, 인증된 사용자 정보 제공, 업무별 접근 권한 판단 |
| 키파일 기능 | 기존 `Ed25519KeyFile`을 활용한 서명키 로딩·제공 |

위 책임 구분을 기준으로 상세화한다. `Ed25519KeyFile`이 구현되어 있다는 점은 사용자 제공 정보이며, 실제 JWT 연계 가능 여부는 설계 단계에서 확인한다. (확인: 대화 합의·사용자 제공 정보)

## 기능·할 일

다음은 대화에서 합의한 범위다. (확인)

| 기능·할 일 | 범위·정책 |
| --- | --- |
| 로그인 토큰 발급 | 로그인마다 독립된 Access·Refresh 발급. 여러 기기 동시 로그인 허용 |
| 로그인 식별 | 로그인마다 UUID v4 생성. Access JWT의 최상위 `sid`와 Refresh 행의 `session_id`에 같은 ID를 넣고, 갱신해도 유지 |
| Access 발급·검증 | Ed25519 비대칭 서명을 사용하는 JWT. 유효기간 10분. 각 API에서 공개키로 검증 |
| Refresh 관리 | 암호학적 난수 문자열 사용. DB에는 원문 대신 해시 저장. 로그인마다 하나를 발급하여 만료·폐기 전까지 반복 사용 |
| 로그인 유지 기간 | 최초 로그인부터 최대 7일. 갱신해도 최종 만료 시점은 연장하지 않음 |
| 토큰 갱신 | Refresh와 최신 계정 상태를 DB에서 확인하고 Access만 새로 발급. Refresh와 만료 시각은 유지 |
| Refresh 반복 사용 | 동일 Refresh로 여러 번 갱신 가능. 여러 탭의 동시 갱신·재시도 허용. 교체 발급과 사용 이력에 따른 재사용 감지는 현재 범위에서 제외 |
| 일반 로그아웃 | 해당 로그인 Refresh 폐기. 웹은 Access·Refresh 쿠키도 제거 |
| 계정 정지·탈퇴 연계 | 해당 계정의 모든 Refresh 폐기, 추가 갱신 차단 |
| 상태·권한 변경 반영 | 로그아웃·정지·탈퇴 이후에도 기존 Access는 만료까지 최대 10분 허용. 권한 변경도 최대 10분 지연 허용 |
| 갱신 시 사용자 정보 구성 | 서버의 최신 사용자·권한 정보를 반영. 클라이언트가 보낸 사용자·권한 정보는 발급 근거로 사용하지 않음 |

현재는 Refresh 교체·재사용 감지 대신 동일 Refresh를 최대 7일 사용하는 정책으로 정한다. 정상 사용자와 유출된 Refresh를 사용하는 주체를 토큰 사용 이력으로 구분하지 않는다. 만료되거나 폐기된 Refresh로는 갱신할 수 없으며, Refresh 폐기 후에도 이미 발급된 Access에는 동일한 최대 10분 지연 정책을 적용한다. (확인: 대화 합의)

## 웹·API 연계

웹과 API는 같은 사이트에서 운영하며, 웹용과 API용 진입점을 구분한다. 발급·갱신·폐기 규칙은 공통으로 두고 전달 방식은 각 접점이 담당한다. (확인)

| 구분 | 웹 | API |
| --- | --- | --- |
| 로그인 발급 결과 | Access·Refresh 쿠키 설정 | 응답 본문으로 Access·Refresh 반환 |
| 갱신 결과 | Access 쿠키만 갱신. Refresh 쿠키와 만료 시각 유지 | 응답 본문으로 새 Access 반환. 기존 Refresh 유지 |
| 인증 요청 | Access 쿠키 | `Authorization: Bearer <access_token>` |
| 갱신 요청 | Refresh 쿠키 | Refresh 전달 위치는 상세화 시 결정 |
| 로그아웃 | 해당 Refresh 폐기·쿠키 제거 | 해당 Refresh 폐기 |

API 갱신과 로그아웃은 Refresh를 JSON 요청 본문으로 전달한다. 구체 계약은 [JWT API](jwt-api/plan.md)를 따른다. 웹의 쿠키 자동 Access 갱신·HttpOnly/Secure·CSRF·캐시 및 오류 계약은 [JWT 웹 연결](jwt-web/plan.md)을 따른다. (확인)

## Access Token 정보 구성

표준 클레임과 로그인 식별용 `sid`는 최상위에 두고, 애플리케이션에서 사용하는 사용자·권한 정보는 커스텀 `user` JSON 객체로 묶는다. `user`는 JSON 문자열이 아닌 객체다. 계정 ID는 `sub`를 기준으로 삼고 `user`에 중복해서 넣지 않는다. (확인)

| 정보 | 구성 |
| --- | --- |
| 발급자·대상 | `iss`, `aud` |
| 계정 ID | `sub` |
| 로그인 ID | `sid`: 해당 로그인 세션의 UUID 문자열 |
| 발급·만료 시각 | `iat`, `exp` |
| 사용자·권한 | 커스텀 `user` 객체. 내부 필드의 이름·타입·의미는 상세화 시 결정 |

위 표는 논의한 기본 구성이다. 표준 클레임의 구체적인 값·검증 계약은 상세 설계에서 정한다. `user`에 담긴 권한도 발급 당시 정보이며, 변경 시 최대 10분 지연을 허용하고 갱신할 때 최신 정보를 반영한다. (확인: 대화 합의)

## 로그인 세션과 토큰 연결

Access JWT의 `sid`로 로그인 단위를 구분한다. 같은 계정의 별도 로그인은 서로 다른 `sid`를 가지며, 한 로그인에서 갱신한 Access는 같은 `sid`를 유지한다. `sub`는 계정을, `sid`는 개별 로그인을 식별한다. (확인: 대화 합의)

세션 ID는 UUID v4를 사용한다. DB의 `tlab_auth_refresh_token.session_id`를 `UUID`로 저장하고, JWT에는 같은 값을 하이픈을 포함한 UUID 문자열로 담는다. 외부에 사용하는 식별자로 순번을 노출하지 않고 생성 시각 정보가 필요하지 않아 난수 기반 v4를 선택한다. UUID는 로그인 식별자이며 인증 비밀값으로 취급하지 않는다. (추론: 설계 선택)

| 위치 | 연결·책임 |
| --- | --- |
| Access JWT | `sub`와 `sid`로 인증된 계정과 로그인 식별. 발급 시 검증한 Refresh 행에서 두 값을 구성 |
| `tlab_auth_refresh_token` | `session_id = sid`, `account_id = sub`에 해당하는 계정. Refresh 해시·로그인 유지 한도·토큰 만료·폐기 상태 소유 |

별도 세션 테이블 없이 Refresh 테이블에서 로그인과 토큰 상태를 관리한다. Refresh는 난수 문자열이며, 갱신은 Refresh 해시로 행을 조회한다. 만료된 Access나 클라이언트가 별도로 보낸 `sid`를 갱신의 인증 근거로 사용하지 않는다. 새 Access의 `sub`·`sid`는 조회한 Refresh 행의 `account_id`·`session_id`에서 구성한다. (확인: 대화 합의)

일반 API 요청은 JWT 서명과 클레임을 검증하여 `sub`·`sid`를 사용하며, DB를 매번 조회하지 않는다. 따라서 해당 로그인의 Refresh를 폐기해도 기존 Access는 만료까지 최대 10분 유효하다. (추론: 기존 지연 정책에 따른 설계)

## Refresh 만료·폐기와 확장 경계

토큰 수명과 로그인 유지 한도를 구분한다. 현재는 두 만료 시점을 최초 로그인부터 7일로 동일하게 지정한다. 갱신은 어느 만료 시각도 연장하지 않는다. 만료는 시각 비교로 판단하며 `expired` 상태값을 별도 저장하지 않는다. (확인: 대화 합의)

| 정보 | 책임 |
| --- | --- |
| `session_created_at` | 최초 로그인 시각. 갱신 시 유지 |
| `session_expires_at` | 최초 로그인부터 168시간 후인 로그인 유지 한도 |
| `created_at` | 해당 Refresh 발급 시각 |
| `expires_at` | 해당 Refresh 만료 시각. 현재 `session_expires_at`과 동일 |
| `revoked_at`, `revoke_reason` | 로그아웃·정지·탈퇴에 따른 강제 폐기 시각·사유. 최초 폐기 결과 보존 |

갱신 시 계정이 로그인 허용 상태이고, Refresh가 미폐기 상태이며, 현재 시각이 `expires_at`과 `session_expires_at`보다 모두 앞서야 한다. 로그아웃은 같은 `session_id`의 미폐기 행 전체를, 정지·탈퇴는 해당 계정의 미폐기 행 전체를 폐기한다. 다른 기기 로그인은 일반 로그아웃의 영향을 받지 않는다. (추론: 처리 계약)

로그인과 계정 상태 변경·전체 폐기 조합은 트랜잭션에서 계정 행을 먼저 잠근다. 로그아웃은 별도 계정 잠금 없이 해당 로그인 미폐기 행을 조건부 폐기한다. 갱신은 행 잠금 없이 Refresh와 계정을 읽고 상태·만료를 확인한다. 동시 종료·상태 변경과 겹친 갱신은 이전 상태로 Access를 발급할 수 있으며, 이후 폐기를 조회한 갱신은 거부한다. 발급된 Access는 발급부터 10분 유효하다. 상세 경합 계약은 [갱신·종료 구현](jwt-refresh-lifecycle/plan.md)을 따른다. 현재 계정 모델에 정지 상태가 없으므로 상태 모델과 로그인 허용 정책 연계는 후속 구현에서 확정한다. (추론: 처리 계약)

추후 Refresh 수명을 짧게 하고 교체 발급을 도입할 수 있도록 두 만료 컬럼을 구분한다. 교체 시 같은 `session_id`·`account_id`·`session_created_at`·`session_expires_at`을 계승하고, 새 토큰의 `expires_at`은 `min(발급 시각 + 토큰 수명, session_expires_at)`으로 계산한다. 토큰 수명 단축만으로 교체 발급이 구현되지는 않으며, 교체의 원자성·폐기 사유·이력 보존·재사용 감지와 앱 처리는 도입 시 별도 설계한다. (추론: 확장 방향)

## 상세화할 항목

다음 항목은 현재 합의와 구분하여 이후 요구사항·설계에서 정한다. (확인: 미결정)

- Refresh 만료·폐기의 SQL 설계안을 바탕으로 앱 처리·검증 계약과 만료·폐기 행의 보관·정리 정책 확정
- 공개키 제공·캐시·키 교체 방식과 기존 Access의 남은 유효기간 보장
- JWT 검증 계약과 `user` 객체에 포함할 데이터·권한의 범위

API 연결과 검증은 [JWT API](jwt-api/plan.md)에 기록한다. 웹 연결과 브라우저 미검증 범위는 [JWT 웹 연결](jwt-web/plan.md)에 기록한다. 키 운영은 후속이다.
