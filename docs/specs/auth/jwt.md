# JWT 기반 로그인 유지 기능 구상

## 목적과 범위

로그인 후 웹과 API에서 인증을 유지하고, Access Token 만료 시 Refresh Token으로 갱신한다. 토큰 발급·갱신·폐기는 직접 구현한다. Keycloak이나 OIDC 제공자 도입을 이번 범위의 전제로 두지 않는다. (확인: 대화 합의)

이 문서는 대화에서 합의한 기능·책임·정책을 정리한 구상이다. 상세 API·DB·검증 계약과 구현 완료 여부를 나타내지 않는다. 미결정 사항이 있어 문서는 draft로 유지한다.

## 책임 구분

| 주체 | 책임 |
| --- | --- |
| 인증 기능 | 로그인 성공 후 토큰 발급, Refresh 저장·교체·폐기, 갱신 시 최신 사용자·권한 정보 반영 |
| 웹·API 접점 | 공통 토큰 규칙을 사용하고 각 전달 방식에 맞게 요청·응답 처리 |
| 각 API 서비스 | Access JWT 검증, 인증된 사용자 정보 제공, 업무별 접근 권한 판단 |
| 키파일 기능 | 기존 `Ed25519KeyFile`을 활용한 서명키 로딩·제공 |

위 책임 구분을 기준으로 상세화한다. `Ed25519KeyFile`이 구현되어 있다는 점은 사용자 제공 정보이며, 실제 JWT 연계 가능 여부는 설계 단계에서 확인한다. (확인: 대화 합의·사용자 제공 정보)

## 기능·할 일

다음은 대화에서 합의한 범위다. (확인)

| 기능·할 일 | 범위·정책 |
| --- | --- |
| 로그인 토큰 발급 | 로그인마다 독립된 Access·Refresh 발급. 여러 기기 동시 로그인 허용 |
| Access 발급·검증 | Ed25519 비대칭 서명을 사용하는 JWT. 유효기간 10분. 각 API에서 공개키로 검증 |
| Refresh 관리 | 암호학적 난수 문자열 사용. DB에는 원문 대신 해시 저장 |
| 로그인 유지 기간 | 최초 로그인부터 최대 7일. 갱신해도 최종 만료 시점은 연장하지 않음 |
| 토큰 갱신 | Refresh를 DB에서 확인하고 새 Access·Refresh 발급. 사용한 Refresh는 폐기 |
| Refresh 재사용 대응 | 교체되어 폐기된 Refresh가 다시 제출되면 해당 로그인에서 파생된 Refresh 전체 폐기·재로그인 요구. 다른 기기의 로그인은 유지 |
| 일반 로그아웃 | 해당 로그인 Refresh 폐기. 웹은 Access·Refresh 쿠키도 제거 |
| 계정 정지·탈퇴 연계 | 해당 계정의 모든 Refresh 폐기, 추가 갱신 차단 |
| 상태·권한 변경 반영 | 로그아웃·정지·탈퇴 이후에도 기존 Access는 만료까지 최대 10분 허용. 권한 변경도 최대 10분 지연 허용 |
| 갱신 시 사용자 정보 구성 | 서버의 최신 사용자·권한 정보를 반영. 클라이언트가 보낸 사용자·권한 정보는 발급 근거로 사용하지 않음 |

Refresh 재사용은 탈취를 증명하지는 않지만, 서버의 발급·교체·폐기 기록을 기준으로 동일하게 처리한다. 여러 탭의 동시 갱신이나 재시도로 발생해도 해당 로그인은 종료한다. Refresh를 폐기한 후에도 이미 발급된 Access에는 동일한 최대 10분 지연 정책을 적용한다. (확인: 대화 합의)

## 웹·API 연계

웹과 API는 같은 사이트에서 운영하며, 웹용과 API용 진입점을 구분한다. 발급·갱신·폐기 규칙은 공통으로 두고 전달 방식은 각 접점이 담당한다. (확인)

| 구분 | 웹 | API |
| --- | --- | --- |
| 발급·갱신 결과 | Access·Refresh 쿠키 설정 | 응답 본문으로 Access·Refresh 반환 |
| 인증 요청 | Access 쿠키 | `Authorization: Bearer <access_token>` |
| 갱신 요청 | Refresh 쿠키 | Refresh 전달 위치는 상세화 시 결정 |
| 로그아웃 | 해당 Refresh 폐기·쿠키 제거 | 해당 Refresh 폐기 |

API 갱신 요청은 Refresh를 요청 본문으로 전달하는 방식을 제안했으며, 아직 확정하지 않았다. 웹의 `HttpOnly`·`Secure` 쿠키와 CSRF 방어도 제안한 항목으로, 상세 정책을 구체화할 때 확정한다. (추론: 제안)

## Access Token 정보 구성

표준 클레임은 최상위에 두고, 애플리케이션에서 사용하는 사용자·권한 정보는 커스텀 `user` JSON 객체로 묶는다. `user`는 JSON 문자열이 아닌 객체다. 계정 ID는 `sub`를 기준으로 삼고 `user`에 중복해서 넣지 않는다. (확인)

| 정보 | 구성 |
| --- | --- |
| 발급자·대상 | `iss`, `aud` |
| 계정 ID | `sub` |
| 발급·만료 시각 | `iat`, `exp` |
| 사용자·권한 | 커스텀 `user` 객체. 내부 필드의 이름·타입·의미는 상세화 시 결정 |

위 표는 논의한 기본 구성이다. 표준 클레임의 구체적인 값·검증 계약은 상세 설계에서 정한다. `user`에 담긴 권한도 발급 당시 정보이며, 변경 시 최대 10분 지연을 허용하고 갱신할 때 최신 정보를 반영한다. (확인: 대화 합의)

## 상세화할 항목

다음 항목은 현재 합의와 구분하여 이후 요구사항·설계에서 정한다. (확인: 미결정)

- 웹 쿠키 보호 속성·범위와 CSRF 방어 정책
- 웹·API의 구체적인 경로·요청·응답 및 토큰 전달 계약
- Refresh 저장 구조와 교체·재사용 감지를 보장할 처리 계약
- 공개키 제공·캐시·키 교체 방식과 기존 Access의 남은 유효기간 보장
- JWT 검증 계약과 `user` 객체에 포함할 데이터·권한의 범위

현재 문서는 기능 구상을 보존하며, 위 항목의 상세 설계나 구현·실행 검증은 수행하지 않았다.
