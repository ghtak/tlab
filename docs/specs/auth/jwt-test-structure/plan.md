# JWT/auth 테스트 구조 조사와 변경

## 목적과 범위

기능이 추가될 때 기존 테스트에 시나리오를 이어 붙이는 비용과 실패 원인 식별 문제를 줄인다. 테스트의 계약과 실제 PostgreSQL 격리, 준비 조건 확인, 실패 검출을 유지한다. 운영 코드·공개 계약·스키마·의존성은 바꾸지 않는다. API 쿼리 토큰 로그는 사용자 결정에 따라 범위 밖이다. 이 요청에서 조사부터 구현·검증까지 승인되었다. (확인)

## 조사와 설계

- 기존 `local_login_http_contracts`는 계정 생성, HTTP 로그인·갱신·로그아웃, usecase 발급, 삽입·commit 실패, 탈퇴 잠금, 입력과 계정 상태, 저장 오류를 한 스키마에서 이어 실행했다. 뒤쪽 실패 검증의 Refresh 행 수 `3`은 앞쪽 성공에 의존했고, 앞부분 실패는 뒷부분 실행을 막았다. 독립 시나리오 10개로 나누고 각 실패·경합에서 초기 행 수 0을 검증한다. API 전체 흐름은 의도적인 연쇄이므로 보존한다. (확인·추론)
- Refresh repository와 lifecycle의 스키마 생성·마이그레이션·panic 후 정리 코드는 경로만 달랐다. `auth/test_support.rs`에 실제로 동일한 DB 준비·정리만 모았다. 각 테스트의 계정·토큰, 시간, 행동과 검증은 해당 테스트에 남긴다. 로그인은 Container 및 HTTP 준비가 달라 별도 격리 준비를 유지했다. 테스트별 고유 스키마, spawn 결과를 받은 뒤 DROP, 실제 잠금 준비 확인과 시간 제어 방식을 유지한다. (확인)
- extractor는 동일 서명·클레임 조합을 token 테스트와 다시 검사하고 실패 사례 이름도 없었다. 실제 토큰의 변조 서명 한 사례로 verifier 거부가 HTTP 401/Bearer로 전달되는지 남기고 헤더 거부 사례에 이름을 붙였다. 상세 암호·클레임 조합은 실제 서명으로 검증하는 token 테스트에 남는다. 성공 시 DB 없이 Json 본문과 공존하는 검증도 유지한다. (확인·추론)
- token의 세부 경계, repository의 저장 제약과 lifecycle의 트랜잭션·경합은 서로 다른 계약이므로 삭제하지 않았다. `create_local_user`의 준비는 HTTP와 별도 마이그레이션 요구가 있어 공용화하지 않았다. (추론)

## 전후 핵심 계약 매핑

| 계약과 책임 | 변경 전 | 변경 후 |
| --- | --- | --- |
| 실제 Ed25519 키·서명, 다른 키·변조·알고리즘, 필수 클레임, 정책·만료 경계 | token 및 extractor에서 세부 경우 중복 | token 테스트 전체 보존, extractor는 대표 변조와 HTTP 거부 연결 |
| Refresh 난수·원문 해시, 저장 제약·조회·상태·폐기와 기기 격리 | token, repository, lifecycle 및 로그인 연쇄 | 각 소유 계층에서 보존; 로그인 발급 행과 세션 연결도 유지 |
| 로그인 usecase 성공·별도 세션, 서명·삽입·commit 실패와 rollback | 거대 로그인 테스트의 앞선 세션 수에 의존 | 독립 발급 및 실패 테스트, 실패 후 행 0 검증 |
| 탈퇴와 로그인 실제 계정 잠금 경합 | 같은 거대 테스트 안에서 선행 성공 행 3개에 의존 | 독립 스키마·행 0, `pg_blocking_pids`로 대기 확인 후 commit |
| Refresh 양쪽 독립 만료, 폐기·비활성 계정 | lifecycle | 두 만료 컬럼을 각각 만료시키고 복원하는 검증과 활성 계정 폐기 검증 유지 |
| Refresh/logout 경합, 오류가 InvalidRefresh로 오인되지 않음 | lifecycle | 각 시나리오 유지, 동시 결과의 `Internal` 명시 거부 보존 |
| 실제 Refresh 행 잠금과 commit 상태 재조회; 호출자 rollback | repository | 실제 행 잠금 경합 및 insert/revoke rollback 보존 |
| HTTP 로그인→인증→갱신→로그아웃→재갱신 거부, 기존 access 유효 | 거대 로그인 테스트의 앞부분 | 독립 HTTP 흐름으로 보존 |
| 잘못된 자격증명·계정 상태·입력·용량·공유 permit·Internal 오류 | 거대 로그인 테스트 후반부 | 목적별 독립 테스트와 기존 표 사례 유지 |
| DB 없는 Bearer 추출 및 Json 공존 | extractor | 성공 및 헤더·서명 거부 유지 |

서로 다른 계층에서 같은 조건을 전부 재검증하는 대신 각 경계에서 별도로 발생할 수 있는 실패는 남긴다. 예를 들어 서명 검증 자체와 HTTP 오류 변환, 저장소 rollback과 usecase commit 실패는 서로 대체할 수 없다. (추론)

## 검증과 자체 점검

- `cargo test -p tlab-app auth:: -- --ignored`: 개발 PostgreSQL의 고유 임시 스키마를 사용하고 기본 병렬 실행, 28 passed. 각 테스트가 스키마를 독립 생성·정리한다. 테스트 DB 환경변수 원문은 기록하지 않는다. (확인)
- `cargo test -p tlab-app auth::login_local::tests::login_rechecks_account_after_withdrawal_lock -- --ignored --exact`: 단독 1 passed. 처음 축약 필터와 `--exact`를 함께 사용한 실행은 0개여서 검증으로 세지 않고 전체 이름으로 재실행했다. (확인)
- `cargo test --workspace --locked`: 성공. 앱 테스트 23 passed, DB 요구 28 ignored; 별도 DB 실행으로 auth ignored를 확인했다. workspace의 다른 ignored 테스트는 이 명령에서 실행하지 않았다. (확인)
- `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets --locked -- -D warnings`, `git diff --check`: 성공. 첫 clippy는 이동 중 미사용 변수로 실패했고 제거 후 재실행했다. (확인)
- 운영 코드의 분기·주입점·setter나 의존성 변경은 없다. 테스트 전용 모듈 선언과 지원 코드만 추가했다. 테스트 격리 실패 시 기존 방식처럼 스키마 생성 이전 실패는 정리할 대상이 없고, scenario panic은 join 이후 DROP한다. 프로세스 강제 종료 시 남는 스키마는 기존 방식과 같다. DB 자원 소모는 로그인 시나리오를 병렬로 분리해 증가한다. (확인·추론)

## 테스트 가이드 보완 검토

기존 `guide-test.md`는 이미 계약 중심 검증, 같은 실패 반복 방지, 실제 의존성 격리·정리, 준비 조건 확인, 의도와 가독성을 명시한다. 아래는 이를 적용할 실행 기준 제안이며 가이드 자체는 이번에 수정하지 않았다. (확인)

| 추천 문구 | 발견 사례와 이유 | 적용 예외 |
| --- | --- | --- |
| “하나의 테스트에 서로 독립적인 목적이 이어지면 각 목적을 독립 준비·실행·검증으로 분리하고, 선행 결과에 의존하는 수치가 실제 계약인지 확인한다.” | 로그인 오류 행 수가 앞선 세션 3개에 의존하여 실패 지점과 실행 범위가 연결됐다. | 로그인→갱신→로그아웃처럼 순서 자체가 계약인 흐름은 함께 유지한다. |
| “같은 거부 계약의 입력 표에는 비밀이 아닌 사례 이름을 두어 실패 사례를 식별한다. 다른 원인이나 상태 전이가 필요한 경우 별도 테스트를 고려한다.” | extractor 거부 표의 어느 헤더가 실패했는지 기존 assertion만으로 식별하기 어려웠다. | 단일 사례 또는 입력이 안전하게 식별되는 간단한 표에는 불필요하다. 비밀 입력은 출력하지 않는다. |
| “공통 준비는 반복되는 자원 생성·정리에 한정하고, 시나리오를 구별하는 입력·행동·기대값은 호출부에서 확인할 수 있게 둔다.” | Refresh 격리 코드는 동일했지만 로그인 Container 준비는 다르며, 토큰·계정 상태는 시나리오별 의미가 있다. | 긴 설정이 본질적으로 동일하고 이름과 인수로 의도가 충분히 드러나면 더 넓게 공유할 수 있다. |
| “중복을 제거할 때 각 계층에서 새로 발생할 수 있는 실패와 대표 연결 검증을 먼저 대응시킨다.” | token의 서명 상세는 extractor에서 중복이지만 verifier 거부를 HTTP challenge로 변환하는 계약은 별개다. | 경계마다 서로 다른 정책이나 장애가 있으면 같은 입력도 각 계층에서 검증할 수 있다. |

테스트당 assertion 하나, 줄 수·파일 수 제한은 제안하지 않는다. 한 계약을 입증하는 여러 결과와 순서 자체가 의미 있는 전체 흐름은 함께 검증할 수 있다. (추론)
