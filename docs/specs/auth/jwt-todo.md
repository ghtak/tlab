# JWT 구현 순서와 검증 계획

## 연결 문서

| 관계 | 대상 | 설명 |
| --- | --- | --- |
| realizes | [SPEC-AUTH-JWT](../../specs/auth/jwt.md) | JWT 로그인 유지 기능 구상과 현재 정책 |

## 목적과 기준

JWT 기능을 책임별 작업 단위로 구현하고, 각 단계에서 실제 동작을 검증한 뒤 다음 단계에 연결한다. 시간·트랜잭션·동시성의 재현 가능성을 고려한다. 아래 순서와 경계는 구현 제안이며, 구현 완료를 나타내지 않는다. (추론)

기준은 최신 `docs/specs/auth/jwt.md`와 [Refresh SQL 설계안](../../../tlab-app/migrations/0002_create_tlab_auth_refresh_token.sql)이다. 이전 대화에서 논의한 Refresh 교체 방식과 달리, 현재는 같은 Refresh를 최대 7일 반복 사용하고 Access만 갱신한다. `sid`로 로그인 단위를 식별하며 Refresh 교체·재사용 감지는 현재 범위에서 제외한다. (확인: 문서·SQL)

앱 구조는 [앱 개발 구조](../../architecture/app-structure.md)를 따른다. 로그인·갱신·로그아웃의 시나리오는 각 slice에 두고, 실제로 공유하는 토큰 작업과 저장소 API는 auth 공용 범위에 둔다. (추론: 구현 제안)

## 구현 순서와 범위

다음은 단계별 구현 범위와 완료를 판단할 검증 기준이다. 아직 실행하거나 검증하지 않았다. (추론: 계획)

| 순서 | 구현 범위·책임 | 핵심 검증 |
| --- | --- | --- |
| 1. 공통 계약 확정 | 클레임·인증 결과 타입, 로그인 허용 상태, 오류 구분, 시간 기준 결정 | 웹·API가 같은 인증 결과를 사용할 수 있는지 확인 |
| 2. 토큰 발급·검증 | 기존 Ed25519 키 연계, Access 서명·검증, Refresh 난수 생성·해시 처리 | 변조·다른 키·잘못된 발급자/대상·만료 거부, 10분 경계 |
| 3. Refresh 저장 | entity·repository, 조회·폐기·계정 잠금, 기존 migration 설계안 연계 | 실제 PostgreSQL에서 제약·잠금·rollback 확인 |
| 4. 로그인 발급 | 기존 비밀번호 인증에 로그인 ID·Refresh 저장·Access 발급 연결 | 로그인별 독립 sid, 원문 미저장, 저장 실패 시 토큰 미반환 |
| 5. 갱신·종료 | Refresh 검증, 최신 계정·권한 조회, Access 갱신, 로그아웃·전체 폐기 | 7일 한도 유지, 반복 갱신 허용, 폐기 후 갱신 거부, 기기별 격리 |
| 6. API 연계 | 로그인·갱신·로그아웃 응답, Bearer 인증 추출, 보호 API 연결 | 실제 Router로 로그인 → 보호 API → 갱신 → 로그아웃 검증 |
| 7. 웹 연계 | 별도 웹 진입점, 쿠키 설정·갱신·제거, CSRF 방어 | 실제 브라우저에서 쿠키·CSRF·만료 후 갱신 검증 |
| 8. 운영 연결 | 공개키 제공·교체, 설정 오류, 비밀값을 제외한 진단 로그 | 키 교체 전후 토큰 검증, 잘못된 설정의 시작 실패 |

현재 계정 모델에 정지 상태가 없으므로 전체 Refresh 폐기 기능을 구현하되, 정지 시나리오 연결은 상태 정책을 확정한 뒤 진행한다. (확인: 현재 문서 / 추론: 구현 제안)

## 테스트하기 위한 책임 경계

다음 경계를 기준으로 구현한다. (추론: 제안)

- **시간 통제:** 토큰·만료 정책은 명시적인 현재 시각을 받거나 작은 시계 의존성을 사용한다. 10분·7일을 실제로 기다리는 테스트는 만들지 않는다. DB 잠금 대기 이후의 만료 판단은 별도로 검증한다.
- **JWT 검증 독립:** DB·HTTP 없이 테스트 키로 실제 서명·검증을 실행한다. 서명 라이브러리를 mock으로 대체한 성공 결과보다 공개 계약을 직접 검증한다.
- **트랜잭션 소유:** usecase가 트랜잭션을 소유하고 repository는 전달받은 DB context로 실행한다. repository는 임의로 commit하지 않는다. SQL·제약·동시성은 격리된 실제 PostgreSQL에서 확인한다.
- **웹·API 정책 공유:** 같은 usecase를 호출하고 쿠키·본문 변환은 접점에서 처리한다. 공통 인증 정책 테스트를 두 벌로 복제하지 않고 전달 방식별 계약을 각각 검증한다.
- **필요한 의존성만 교체:** 시간이나 발급 실패를 통제할 필요가 있을 때 trait을 도입한다. 모든 repository에 일괄 적용하지 않는다.

## 주요 실패·동시성 검증

다음은 정상 기능과 별개로 확인해야 할 계약이다. (추론: 계획)

1. **계정 폐기와 로그인·갱신의 경합:** 같은 계정 잠금 규칙으로 처리해 폐기 이후 새 Refresh가 살아남지 않도록 한다.
2. **응답 전 실패:** 서명·저장·commit 중 실패하면 사용할 토큰을 성공 응답으로 내보내지 않는다.
3. **지연 허용:** 로그아웃 후 Refresh는 거부하지만 기존 Access는 만료까지 허용한다. 테스트도 즉시 차단을 기대하지 않고 합의한 최대 10분 지연 정책을 기준으로 작성한다.

## 작업 단위와 선행 결정

구현은 다음 작업 단위로 묶고, 각 작업에서 필요한 테스트까지 완료한다. (추론: 제안)

| 작업 단위 | 범위 |
| --- | --- |
| 1. 토큰 기반·저장 | 공통 계약, 키 연계, 발급·검증, Refresh entity·repository |
| 2. 로그인·갱신·종료와 API | 시나리오·트랜잭션, Bearer 연계, API 요청·응답 |
| 3. 웹 | 쿠키 전달, 웹 진입점, CSRF 방어, 브라우저 검증 |
| 4. 키 운영 | 공개키 제공·교체와 배포·운영 검증 |

키 식별·검증 계약은 첫 작업부터 고려한다. 웹 구현 전에는 쿠키·CSRF 정책을, 발급 구현 전에는 `user`에 넣을 데이터와 권한의 원본을 정한다. API 경로·Refresh 전달 위치 등 미결정 계약도 해당 접점을 구현하기 전에 확정한다. (추론: 선행 조건)

## 구현·변경 기록

구현 순서·범위·검증 계획을 대화에서 정리해 저장했다. 인증 기능 구현이나 테스트 실행은 수행하지 않았다. (확인)

토큰 기반 부분을 `auth::token`에 구현했다. 기존 Ed25519 키를 재사용한 Access 발급·공개키 검증(10분·필수 클레임·user 객체), Refresh 난수·SHA-256을 제공한다. 토큰 테스트 7개 및 workspace 테스트가 통과했다. 설계·계약·명령별 결과와 후속 범위는 [PLN-AUTH-JWT-TOKEN](./jwt-token/plan.md)에 기록했다. Refresh 저장·7일 만료 판단, 로그인·HTTP 연결과 키 운영은 이번 구현에 포함하지 않았다. (확인)
