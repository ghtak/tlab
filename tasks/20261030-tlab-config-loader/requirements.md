# tlab 설정 Loader 요구사항

상태: 완료 · 사용자 확정. 이번 요청의 산출물은 요구사항 문서이며, 구현·설계 완료를 의미하지 않는다.

## 1. 목적과 사용 맥락

- {사용자는 제시한 `Loader` 코드와 테스트에 해당하는 설정 로딩 기능을 `tlab`에 추가하기 위한 요구사항 작성을 요청했다.}-측정함
- {목적은 `tlab`을 사용하는 Rust 코드가 설정 파일 및 지정한 접두사의 환경변수를 읽고, 결과를 `config::Config` 또는 호출자가 정의한 타입으로 얻을 수 있게 하는 것이다.}-추론함
- {로딩 시점은 호출자가 `load` 또는 `try_deserialize`를 호출하는 때이며, 자동 초기화나 전역 설정 저장은 제시되지 않았다.}-측정함

## 2. 확인한 현재 상태와 출발 가정

| 구분 | 확인 내용과 근거 |
| --- | --- |
| 기존 오류 계약 | {`tlab/src/error.rs`는 `Error::Internal(anyhow::Error)`와 `Result<T>`를 정의하고, `tlab/src/lib.rs`에서 공개한다.}-측정함 |
| 현재 의존성 | {`tlab/Cargo.toml`의 의존성은 `anyhow`와 `thiserror`이며, `config`와 `serde`는 선언되어 있지 않다.}-측정함 |
| 현재 모듈 | {확인한 `tlab` 소스에는 설정 Loader, `tracing` 모듈, `test_support` 모듈이 없다.}-측정함 |
| 제시 코드의 공개 API | {`Loader`의 필드는 비공개이며, 공개 생성자는 `from_file(PathBuf)`이다. `env_prefix`, `load`, `try_deserialize`가 제공된다.}-측정함 |
| 외부 사용과 내부 테스트의 차이 | {환경변수 단독 테스트는 비공개 필드를 직접 초기화하므로, 제시한 공개 API만으로 외부 호출자가 같은 구성을 만들 수 없다.}-추론함 |
| 기존 테스트 적용 가능성 | {YAML 테스트는 현재 없는 `crate::tracing::Config`를 사용하므로, 제시한 테스트 전체를 현재 저장소에 그대로 적용할 수 없다.}-추론함 |

위 내용은 저장소 파일 및 사용자가 제시한 코드의 정적 확인 결과다. 의존성 동작을 실행으로 검증한 결과는 아니다.

## 3. 범위와 제약

### 포함할 기능 — 제시 코드에서 도출한 초안

- {설정 파일 읽기, 선택적인 환경변수 소스 결합, `config::Config` 반환, `serde::de::DeserializeOwned` 타입으로의 역직렬화를 포함한다.}-추론함
- {사용자 추가 답변에 따라 환경변수만으로 읽는 구성을 공개 기능으로 포함한다. 공개 생성 API의 구체적인 형태는 설계에서 정한다.}-측정함
- {사용자 추가 답변에 따라 YAML 역직렬화 검증에는 테스트 전용 구조체를 사용한다. `tracing::Config`는 이번 작업에서 추가하지 않고, 개별 모듈의 설정 구성은 이후 작업으로 남긴다.}-측정함
- {제시된 `PathBuf`, `config`, `serde`, `anyhow::Context`와 기존 `crate::Error`·`crate::Result` 사용을 기술적 출발 조건으로 보존한다. 의존성 버전은 설계에서 정한다.}-추론함
- {사용자가 Q4의 모듈 파일을 `config.rs`로 지정했다.}-측정함
- {현재 크레이트 구조에 따라 `tlab/src/config.rs`에 공개 `config` 모듈을 두고, 외부 호출 경로는 `tlab::config::Loader`로 해석한다.}-추론함
- {설정 파일을 생성하거나 수정하지 않으며, 없는 파일을 자동 생성하지 않는 동작을 유지한다.}-추론함
- {테스트에서 변경하는 환경변수는 복구하고, 환경변수를 사용하는 테스트끼리 간섭하지 않도록 해야 한다. 제시된 테스트가 잠금과 복구용 도우미를 사용한 데서 도출한 검증 조건이다.}-추론함

### 이번 초안에 추가하지 않은 범위

{자동 파일 생성, 기본 설정 파일 배포, 파일 변경 감시, 자동 재로딩, 여러 설정 파일 병합, 전역 설정 저장, CLI 인자 소스는 요청에서 확인되지 않아 범위에 포함하지 않았다.}-추론함

{`tracing` 기능과 개별 모듈의 설정 타입 추가는 사용자 추가 답변에 따라 이번 범위에서 제외한다.}-측정함

{현재 단계에서는 운영 코드·의존성을 변경하지 않고 요구사항 문서와 작업 상태만 작성한다.}-측정함

## 4. 기대 동작과 관찰 가능한 성공 기준

아래 항목은 제시 코드·테스트와 사용자 답변을 반영하여 사용자가 확정한 요구사항이다. 실행 검증이 완료된 사실을 뜻하지 않는다.

| ID | 요구사항 초안 | 달성 여부를 판단할 관찰 기준 | 근거 성격 |
| --- | --- | --- | --- |
| R1 | 파일 경로로 Loader를 생성하고 설정을 읽는다. | TOML 파일의 `name = "tlab"`을 읽어 `get_string("name")`이 `"tlab"`을 반환한다. | 제시 API·테스트에서 추론함 |
| R2 | `config`의 파일 탐색으로 설정 소스를 찾지 못하면 오류를 반환하고 파일을 생성하지 않는다. | 지정 경로와 `config`가 탐색하는 후보 파일이 모두 없으면 `Err`이며, 호출 후에도 해당 경로가 없다. 후보 파일 탐색·선택은 `config`에 위임한다. | 사용자 후속 지시를 측정함 |
| R3 | 접두사에 해당하는 환경변수를 설정 소스로 사용하며, 파일 없이도 공개 API로 로딩할 수 있다. | 외부 호출자가 파일을 지정하지 않고 `{PREFIX}_TRACING__CONSOLE__FILTER=debug`를 읽어 `tracing.console.filter`에서 `"debug"`를 얻는다. 여기서 `tracing`은 테스트 데이터의 키이며 실제 tracing 모듈을 요구하지 않는다. | 공개 기능 포함은 사용자 답변을 측정함; 키 매핑은 제시 코드·테스트에서 추론함 |
| R4 | 환경변수 매핑 방식을 유지한다. | 접두사 구분자 `_`, 계층 구분자 `__`, `try_parsing(true)`를 사용한다. 숫자·불리언 환경변수로 타입 역직렬화가 되는지 검증한다. 구체적인 파싱 세부 규칙은 의존성 확인 후 설계에 기록한다. | 제시 코드에서 추론함 |
| R5 | 파일과 환경변수를 함께 구성하고, 동일 키는 환경변수를 우선한다. | 같은 키에 서로 다른 값을 지정하면 환경변수 값을 얻고, 파일에만 있는 키는 파일 값을 유지한다. | 환경변수 우선은 사용자 답변을 측정함; 파일 전용 키 유지는 병합 동작에서 추론함 |
| R6 | 설정 결과를 호출자가 직접 조회할 수 있다. | 공개 API의 `load(self)`가 `crate::Result<config::Config>`를 반환하고, 외부 호출 코드에서 값을 조회할 수 있다. | 제시 시그니처에서 추론함 |
| R7 | 호출자 타입으로 역직렬화할 수 있다. | `T: DeserializeOwned`에 대해 `try_deserialize<T>(self) -> crate::Result<T>`를 사용할 수 있고, YAML의 중첩 구조·문자열·정수·불리언·경로 값을 테스트 전용 구조체로 역직렬화한다. 실제 `tracing::Config`에 의존하지 않는다. | 테스트 전용 구조체는 사용자 답변을 측정함; 역직렬화 계약은 제시 API·테스트에서 추론함 |
| R8 | 로딩 및 역직렬화 실패를 기존 오류 타입으로 반환한다. | 존재하지 않는 파일, 잘못된 파일 내용, 타입이 맞지 않는 값에 대해 `Error::Internal`을 반환한다. 역직렬화 오류에는 `failed to deserialize config` 문맥과 원인 오류가 유지된다. | 제시 오류 처리에서 추론함 |
| R9 | 공개 사용과 기존 기능의 호환성을 확인한다. | 외부 호출 관점에서 공개 API 사용을 검증하고, 기존 `Error`·`Result` 계약 및 기존 테스트가 유지된다. 파일·환경변수 테스트는 임시 자원을 정리한다. | 라이브러리 추가 목적 및 제시 테스트에서 추론함 |

### 우선순위: 사용자 확정

{제시 코드는 파일 다음에 환경변수 소스를 추가한다.}-측정함

{사용자가 Q3에 대해 환경변수 우선을 명시했다.}-측정함

동일 키는 환경변수 값을 우선하고 파일에만 있는 값은 유지하는 것을 R5의 성공 기준으로 삼는다. 선택한 `config` 버전의 소스 결합 동작과 충돌 테스트를 설계·구현 단계에서 확인한다.

## 5. 검증 계획과 실제 확인 범위

- {직접 확인한 자료는 루트 `Cargo.toml`, `tlab/Cargo.toml`, `tlab/src/lib.rs`, `tlab/src/error.rs`, `tlab` 소스 파일 목록과 사용자 제시 코드이다.}-측정함
- {아직 Loader를 구현하지 않았고, 제시 테스트·Cargo 테스트·의존성 파싱 동작을 실행하지 않았다.}-측정함
- 구현 후 검증 계획: R1~R9에 해당하는 파일 로딩·없는 파일·환경변수 매핑·파일과 환경변수 충돌·YAML 역직렬화·오류 반환·외부 공개 API 사용을 확인하고 기존 테스트를 실행한다. 현재 없는 `test_support`의 구체적 구성은 설계에 맡긴다.

## 7. 완료 조건과 다음 단계

{Q1~Q4의 범위·우선순위·모듈 위치에 대한 사용자 답변을 반영했고, 사용자가 요구사항을 완료로 변경하도록 명시했다.}-측정함

요구사항 작업은 `complete`로 기록한다. 이후 설계에서는 환경변수 단독 생성 API, 의존성 구성, 오류·테스트 방식을 구체화한다. 요구사항 완료를 설계나 구현 완료로 간주하지 않는다.

후속 변경(rev-03): 사용자가 파일 탐색·읽기를 `config`에 위임하는 방향으로 되돌리도록 요청했다. R2의 기존 “지정 경로가 없으면 후보가 있어도 실패” 해석을 폐기하고 의존성의 탐색 규칙을 수용한다. 정확한 경로만 읽어야 한다는 추가 제약은 두지 않는다.-`측정함`
