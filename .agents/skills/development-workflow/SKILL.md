# 개발 진행

개발 작업을 요구사항 정리 → 설계 → 구현·검증 → 자체 점검 순서로 수행한다.
변경 크기로 적용 범위를 제한하지 않고, 불확실성·영향 범위·복구 위험에 맞춰 각 단계의 깊이를 정한다.
전체 진행과 문서·승인 상태는 이 스킬이 관리하고, 전문적인 조사·요구사항·설계·검증·리뷰가 필요하면 해당 스킬을 참조한다.
각 단계의 결과를 작업 문서에 갱신하고 사용자 승인을 받은 뒤 다음 단계로 진행한다.
사용자의 명시적인 요청과 이미 합의된 진행 방식을 우선한다.

## 호출 조건

사용자가 `개발 진행` 스킬 또는 `$development-workflow` 사용을 명시적으로 요청한 경우에만 적용한다.
단순히 “개발해 줘”, “수정해 줘”, “작업을 진행해 줘”라고 요청한 것만으로 이 스킬을 선택하지 않는다.

## 참조 문서

경로는 이 `SKILL.md`가 있는 디렉터리를 기준으로 해석한다.

- 시작할 때 [개발 진행 가이드](../../../docs/agent/development-workflow/index.md)를 읽고 수행 깊이·수행 흐름·전문 스킬 참조 기준을 적용한다.
- 구현할 때 [구현 가이드](../../../docs/architecture/guide-impl.md)와 [테스트·검증 가이드](../../../docs/architecture/guide-test.md)를 읽고 적용한다.
- 작업 문서를 작성·갱신할 때 [문서 관리 규칙](../../../docs/agent/document-management/index.md)을 적용한다. 기존 문서를 재사용하고, 없으면 단일 통합 명세로 시작하여 단계별로 보완한다.
- `docs/notes`는 사용자가 명시적으로 참조를 요청한 문서만 읽는다. 읽은 노트를 확정 요구사항으로 간주하지 않는다.

## 수행

1. **요구사항 정리:** 사용자 요청과 관련 명세·코드·호출자에서 목적, 범위, 기대 동작과 완료 조건을 정리한다. 불확실성·계약·영향 범위·복구 위험을 살펴 필요한 조사와 요구사항 구체화의 깊이를 정한다. 작업 문서에 요구사항·제안·미결정 사항과 현재 상태를 반영하고 승인을 요청한다.
2. **설계:** 요구사항 승인 후 목적에 필요한 변경안과 책임·경계·계약·선택 이유·검증 방법을 정한다. 기존 구조를 우선 활용하고, 경계 조정이 필요하면 근거와 영향을 검토한다. 문서를 갱신하고 설계 승인을 요청한다. 승인 전에는 구현하지 않는다.
3. **구현·검증:** 설계 승인 후 필요한 범위를 구현하고 프로젝트의 필수 검사와 변경에 맞는 실행 검증을 수행한다. 실패·환경 문제·미실행을 구분하여 실제 변경과 검증 결과를 문서에 반영하고 승인을 요청한다.
4. **자체 점검:** 구현·검증 승인 후 최종 diff를 완료 조건·호출자·오류 처리·부작용·회귀 위험과 대조한다. 결함을 수정하면 영향받는 검증을 다시 수행한다. 문서에 조치·남은 사항을 반영하고 최종 확인을 요청한다. 자체 점검에 정식 코드 리뷰 점수나 통과 판정을 부여하지 않는다.

각 단계에서는 검토 가능한 결과와 문서 링크를 제시한 후 승인을 요청하고 다음 단계는 대기한다.
최초 구현 요청, 응답 대기 시간, 수정 의견만으로 다음 단계 승인을 추정하지 않는다.
승인한 범위와 근거를 기록하고 같은 승인을 반복 요청하지 않는다. 승인된 계약을 실질적으로 바꿀 때는 변경 부분의 재승인을 받는다.
사용자가 여러 단계를 명시적으로 함께 승인하거나 진행 방식을 바꾸면 그 범위와 방식을 따른다.

각 단계에서 필요한 전문 스킬만 가이드의 기준에 따라 읽고 적용한다. 모든 스킬을 순서대로 실행하지 않는다.
전문 스킬은 해당 작업의 결과를 제공하고, 이 스킬은 그 결과를 기존 작업 문서와 다음 단계에 연결한다. 기존 문서·승인 상태를 이어받으며 중복 산출물이나 승인 요청을 만들지 않는다.
정식 리뷰를 요청받거나 프로젝트에서 요구하면 해당 리뷰 절차와 선행 검사를 적용한다.
요구사항·설계·리뷰만 요청받았다면 그 범위까지만 수행한다. 별도 단계별 문서를 일괄 생성하거나 커밋·PR·게시·배포를 자동 후속 단계로 추가하지 않는다.
