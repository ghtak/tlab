# 작은 변경 처리

작은 변경의 요구사항·설계·구현·검증·자체 점검을 한 흐름으로 수행한다.
사용자의 명시적인 요청과 이미 합의된 진행 방식을 우선한다.

## 참조 문서

경로는 이 `SKILL.md`가 있는 디렉터리를 기준으로 해석한다.

- 시작할 때 [작은 변경 처리 가이드](../../../docs/agent/small-change/index.md)를 읽고 적용 판단·수행 흐름·전환 기준을 적용한다.
- 구현할 때 [구현 가이드](../../../docs/architecture/guide-impl.md)와 [단위 테스트 가이드](../../../docs/architecture/guide-uint-test.md)를 읽고 적용한다.
- 작업 문서를 작성·갱신할 때 [문서 관리 규칙](../../../docs/agent/document-management/index.md)을 적용한다. 기존 문서를 재사용하고 별도 기록이 필요할 때 단일 통합 명세로 시작한다.
- `docs/notes`는 사용자가 명시적으로 참조를 요청한 문서만 읽는다. 읽은 노트를 확정 요구사항으로 간주하지 않는다.

## 수행

1. 사용자 요청과 관련 명세·코드·호출자에서 목적, 범위, 변경 전후의 기대 동작과 완료 조건을 짧게 정리한다. 파일 수보다 계약·영향 범위·복구 위험으로 약식 처리 가능 여부를 판단한다.
2. 기존 구조를 활용하는 최소 변경안과 선택 이유, 실행으로 확인할 조건을 정한다. 중요한 미결정 사항만 확인하고 단계별 승인을 추가하지 않는다.
3. 필요한 범위를 구현하고 프로젝트의 필수 검사와 변경에 맞는 실행 검증을 수행한다. 기존 검증을 재사용하며 필요한 테스트만 추가·보완한다. 실패·환경 문제·미실행과 미확인 범위를 구분한다.
4. 최종 diff를 완료 조건·호출자·오류 처리·부작용·회귀 위험과 대조하여 자체 점검한다. 결함을 수정하면 영향받는 검증을 다시 수행한다. 자체 점검에 정식 코드 리뷰 점수나 통과 판정을 부여하지 않는다.
5. 변경 결과, 검증 명령·결과, 자체 점검의 조치와 남은 사항을 보고한다. 별도 단계별 문서를 일괄 생성하지 않고 기존 기록이나 작업 요약에 근거를 남긴다.

약식 범위를 벗어나면 가이드에 따라 필요한 개별 스킬로 연결하고 기존 근거를 재사용한다. 정식 리뷰를 요청받거나 프로젝트에서 요구하면 해당 리뷰 절차와 선행 검사를 적용한다.
요구사항·설계·리뷰만 요청받았다면 그 범위까지만 수행한다. 커밋·PR·게시·배포를 자동 후속 단계로 추가하지 않는다.
