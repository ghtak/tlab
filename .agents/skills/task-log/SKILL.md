# 작업 기록

작업을 재개하거나 지침·스킬을 개선할 때 필요한 맥락을 기록한다. 상태값이나 작업 간 실행 순서는 관리하지 않는다.

1. 호출자가 지정한 작업 디렉터리를 사용한다. 기존 작업의 디렉터리가 불분명하면 임의로 선택하지 말고 확인한다. 새 작업은 Git 루트의 `tasks/YYYYMMDD-제목` 아래에 둔다. 상태 관리가 필요한 경우 `state-mgmt` 절차에 따라 디렉터리를 준비할 수 있다.
2. 작업 디렉터리의 `task-log.md`가 없으면 최초 요청과 그에 대한 응답을 간결히 요약해 작성한다. 이미 있으면 기존 내용을 보존한다. 최초 응답이나 근거를 확인할 수 없으면 알 수 없다고 기록하고 추측해 채우지 않는다.
3. 중요한 제안, 사용자 또는 실행 주체의 결정, 방향 변경, 작업 진행과 결과를 해당 시점에 기록한다. 대화 전체를 복사하지 말고 이후 이해와 재개에 필요한 내용만 남긴다. 작성·수정 등 실제 수행한 일과 제안만 한 일을 구분한다.
4. 각 항목에 날짜, 내용과 출처를 적고, 해당하면 근거, 영향, 관련 문서 경로를 덧붙인다. 제안, 확정, 보류를 구분하며 명시적으로 확정되지 않은 제안을 결정으로 기록하지 않는다. 불확실한 내용이나 추론은 구분한다.
5. 결정이 변경되면 이전 항목을 지우지 않고 새 항목에 변경 내용과 이전 항목을 연결한다. 민감한 값은 기록하지 말고 필요한 경우 존재와 위치만 적는다.
6. 기록이 길어지면 주제별 문서를 작업 디렉터리 아래에 나누고 `task-log.md`에서 상대 경로로 연결한다. 재개 시에는 필요한 기록만 읽는다. 상태 파일에 문서 연결이 필요하면 `state-mgmt`를 사용하되, 기록 자체를 위해 작업 상태를 임의로 변경하지 않는다.

## 기록 예시

```markdown
# 작업 기록

## 최초 요청과 응답
- 요청 요약: 작업별 상태를 관리할 스킬 작성
- 응답 요약: Git 루트 아래 작업 디렉터리와 상태 파일 사용 제안
- 출처: 사용자 요청과 최초 응답

## 기록

### 2026-10-29 — 상태 관리 범위
- 구분: 확정
- 내용: 작업별 상태와 문서 경로만 관리한다.
- 근거: 스킬 간 순서 의존성을 피한다.
- 출처: 사용자와의 설계 논의
- 영향: 실행 순서는 플레이북이 판단한다.
```
