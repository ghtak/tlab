# 작업 구현

구현의 산출물은 코드뿐 아니라 다른 세션에서 실제 작업과 근거를 확인하고 이어갈 수 있는 작업 문서다. 작업 지시는 무엇을 구현할지, 구현 결과는 어떤 의도·구성·판단으로 실제 수행했는지 설명한다. 파일 목록이나 테스트 통과 요약만으로 결과 기록을 대신하지 않는다.

1. 지정된 작업 디렉터리와 대상 작업, 요구사항·설계·작업 문서 및 관련 코드와 선행 결과를 필요한 만큼 확인한다. 재개라면 이전 구현 차수·남은 사항·피드백도 읽고 현재 코드와 대조한다. 완료 상태만으로 선행 결과나 과거 검증이 현재에도 유효하다고 가정하지 않는다. 범위나 필수 계약이 불명확하면 확인한다.
2. `state-mgmt`에서 구현 단계 전체를 나타내는 `implementation` 항목 하나를 확인하고, 없으면 등록한다. 문서는 `implementation.md`로 연결하고 실제 착수 시 `progress`로 변경한다. 기존 사용자 변경과 이번 변경 범위를 확인한다. 아래 문서 구성에 따라 대표 문서 `implementation.md`와 `implementation/<impl-id>.md`를 준비하고 구현 차수를 정한다. 개별 구현 상태는 대표 문서의 작업 목록에서 관리하고, 착수한 항목을 `progress`로 변경한다. 개별 문서에 목적·계약·완료 조건 및 착수 시점의 확인 내용을 남긴다.
3. [guideline-coding](../guideline-coding/SKILL.md)을 적용해 합의된 범위를 구현한다. 테스트를 선택하거나 작성할 때 [guideline-testing](../guideline-testing/SKILL.md)을 따르고, 변경한 동작과 필요한 연결 동작을 실제 실행해 검증한다.
4. 중요한 판단·변경·검증과 중단이 발생할 때 작업 문서에 근거와 현재 진행 지점을 갱신한다. 종료 시에만 몰아서 기록하지 않는다. 아래 기록 항목과 실제 변경을 대조하고 완료 조건별 충족 근거 및 인계 내용을 정리한다. 별도 검증 결과 문서가 있으면 중복 대신 경로와 확인 범위를 연결한다.
5. 완료 조건과 변경 범위를 확인한 후 해당 구현의 변경만 스테이징하고 `feat: impl-xxx` 형식으로 개별 커밋한다. `impl-xxx`는 실제 구현 ID로 대체한다. 무관한 사용자 변경을 포함하지 않는다. 사용자가 커밋을 제외했다면 스테이징·커밋을 생략하고 그 지시를 기록한다. 커밋할 변경이 없거나 커밋할 수 없으면 이유를 보고한다.
6. 확보한 커밋 해시 또는 미커밋 변경의 경로·차이 확인 기준을 개별 작업 결과에 기록하고 대표 문서의 결과 요약·링크를 갱신한다. 해당 구현·필요한 검증·아래 결과 기록이 완료됐을 때만 대표 문서에서 해당 항목을 `complete`로 변경한다. 모든 하위 구현과 공통 통합 검증·기록이 완료돼야 `state-mgmt`의 `implementation`을 `complete`로 변경한다. 미완료 항목이 남으면 전체 상태는 `progress`로 유지하고 이유와 재개 조건을 기록한다. 커밋 해시를 적은 기록은 자기 자신의 커밋에 포함될 수 없으므로 후속 커밋에 포함하거나 작업 디렉터리에 남긴다.

## 작업 문서와 구현 차수

- 작업이 하나여도 작업 디렉터리의 대표 문서 `implementation.md`와 `implementation/` 하위 개별 구현 문서로 정리한다. 문서 구성을 위해 구현 작업을 불필요하게 쪼개지는 않는다.
- **대표 문서 `implementation.md`:** 입력 요구사항·설계, 구현 대상과 선행 관계, 구현 ID·상태·개발 결과·개별 구현 문서 링크를 담은 목록, 필요한 공유 변경·통합 방법과 공통 검증 기준을 기록한다. 구현 단위를 나누거나 하나로 유지한 이유, 확인한 코드·계약에 근거한 주요 결정과 그 이유도 기록한다. 구현별 결과 요약과 개별 문서의 `구현 결과` 링크를 갱신하며 상세 구현 이력은 중복하지 않는다.
- **개별 문서 `implementation/<impl-id>.md`:** `impl-` 접두사의 구현 ID를 사용한다. 관련 요구사항·설계를 연결하고 목적·계약·완료 조건과 구현 지시를 기록한다. 같은 문서의 `구현 결과` 절에 아래 차수별 기록을 추가하여 구현 지시 원문과 실제 결과를 구분한다.
- 기존 구현 ID를 재사용하고, 없으면 작업 디렉터리 안에서 고유한 `impl-` ID를 부여한다. 기존 문서의 ID가 다른 형식이면 식별 부분을 유지해 `impl-` 형식으로 전환한다. 기존 지시·결과가 다른 문서에 있으면 이력과 차수를 보존해 개별 구현 문서로 옮기고 원래 위치에는 새 문서 링크를 남긴다. 상대 링크와 상태의 문서 경로도 갱신하며 과거 결과를 새 구현으로 기록하지 않는다. 기존 상태 항목의 ID는 문서 ID 전환만을 이유로 변경하지 않는다.
- 최초 구현은 `rev-01`로 기록한다. 같은 시도의 검증 실패 수정·중단 재개는 같은 차수에서 이어가며, 결과 반환 후 합의한 피드백으로 다시 구현하면 다음 차수를 추가한다. 문서만 보완할 때는 차수를 올리지 않고 보완 사실을 남긴다.
- 이전 판단·실패·검증 근거를 보존한다. 과거 사실을 정정할 때는 이유를 명시하며, 과거 검증을 새로 실행한 것처럼 기록하지 않는다. 현재 코드가 바뀌어 기존 근거가 유효하지 않으면 영향 범위를 확인하고 필요한 검증을 다시 수행한다.
- `state-mgmt`에는 구현 단계의 `implementation` 하나만 관리하고 `implementation.md`를 연결한다. `impl-xxx`별 상태는 `implementation.md` 작업 목록의 상태 열에서만 관리하며 상태 도구에 별도로 등록하지 않는다. 상태값은 `pending`, `progress`, `complete`를 사용한다. 재작업에 착수하면 해당 하위 상태와 전체 상태를 `progress`로 되돌린다. 개별 문서에는 상태값을 중복 관리하지 않고 진행 근거와 결과를 남긴다. 구현 완료는 전체 작업이나 리뷰 완료를 의미하지 않는다.

## 대표 문서의 판단 근거와 결정사항

`implementation.md`는 작업 목록뿐 아니라 전체 구현 구성을 판단한 근거를 설명한다. 기존 분할 문서가 있으면 해당 근거를 연결하고, 구현 착수 시 확인하거나 달라진 판단을 보완한다.

- **입력과 분할 근거:** 어떤 요구사항·설계와 실제 코드·선행 결과를 확인했으며, 어떤 동작·책임·검증 경계로 구현 단위를 나눴는지 설명한다. 하나로 유지했다면 그 이유를 기록한다.
- **선행 관계와 수행 방식:** 구현 순서와 의존 관계의 이유를 기록한다. 순차·병렬 수행 등 수행 방식을 결정했다면 계획과 실제 수행을 구분하고, 결정 근거와 제약을 남긴다.
- **공유 변경과 통합 결정:** 공통 파일·인터페이스의 변경 책임, 기존 기능 재사용, 범위에서 제외한 내용과 그 이유, 계약 변경 시 함께 갱신할 대상을 기록한다.
- **검증과 완료 판단:** 구현별 검증 책임과 공통 검증 범위, 실제 환경이 필요한 조건, 미검증 시 완료로 판단할 수 없는 조건을 설명한다. 계획과 실행 결과를 구분하고 상세 근거는 개별 결과 문서로 연결한다.

결정은 확인한 사실·제약 → 선택과 이유가 연결되도록 작성한다. 실제로 검토하지 않은 대안이나 결정되지 않은 수행 방식을 사후에 만들어 넣지 않는다. 분할이나 범위·통합 방법이 바뀌면 변경 이유와 영향도 대표 문서에 갱신한다.

## 문서 출력 형식

- 대표 문서와 개별 문서 모두 제목·문단·목록·표·코드 블록 사이에 빈 줄을 둔다. 한 문단에는 하나의 판단이나 설명을 담는다.
- 문서의 주요 구획은 `##`, 구현 차수는 `###`로 표시한다. 차수 안의 기록 항목은 **굵은 항목명**을 독립된 줄에 놓고, 빈 줄 뒤에 본문을 작성한다. `제목: 내용`을 길게 이어 쓰거나 항목마다 깊은 소제목을 만들지 않는다.
- 판단의 배경과 이유는 문단으로 설명하고, 병렬 항목은 목록으로 정리한다. 작업 관계·검증 결과·완료 조건처럼 같은 기준으로 비교할 내용은 짧은 표로 작성한다. 긴 설명이나 로그를 표 안에 넣지 않는다.
- 문서는 상대 링크로 연결하고, 코드 식별자·파일 경로·짧은 명령은 인라인 코드로 표시한다. 여러 줄 명령은 언어를 지정한 코드 블록에 넣는다.
- 아래 예시의 설명문은 실제 내용으로 바꾼다. 해당하지 않는 항목과 빈 절은 생략하고, 형식을 채우기 위해 같은 근거를 반복하지 않는다.

## 각 차수의 기록 기준

작업 규모에 맞게 절을 합쳐도 되지만 다음 내용을 확인할 수 있어야 한다. 계획·실제 수행·추론·미확인을 구분하며 확인할 수 없는 이력을 추측해 채우지 않는다.

- **입력과 의도:** 적용한 요구사항·설계·선행 결과의 경로, 달성하려는 동작과 완료 조건, 사용자 제약 및 착수 시 확인한 기존 변경.
- **구성과 주요 판단:** 주요 책임·호출 흐름·인터페이스와 재사용 방식, 중요한 선택의 이유와 근거. 작업 지시 복사나 파일 목록으로 대신하지 않는다.
- **실제 변경:** 경로와 바뀐 동작, 확보한 커밋·diff 등 식별 근거. 지시와 달라졌다면 변경 이유와 합의 출처. 경로만 남긴 미커밋 기록이 당시 코드를 정확히 복원해 준다고 주장하지 않는다.
- **검증과 한계:** 선택한 검증의 목적, 실제 명령·작업 위치·필요한 환경, 결과와 확인 범위. 실패 후 수정·재실행, 미실행·미확인 사항과 영향을 남긴다. 민감한 값이나 전체 로그 대신 필요한 요약과 근거 위치를 사용한다.
- **완료 조건과 인계:** 조건별 구현·검증 근거, 남은 일과 통합 주의점. 중단 시 마지막 완료 지점·막힌 이유·다음 실행과 재개 조건을 명시한다. 재진행이면 이전 차수와 피드백별 반영·보류 결과 및 근거를 연결한다.

## 기록 예시

대표 문서는 다음처럼 개별 구현 지시와 결과로 연결한다. 예시 ID 대신 실제 구현 ID를 사용하고 필요한 항목만 작성한다.

```markdown
# Implementation: 작업 제목

## 입력과 분할 근거

요구사항·설계·확인한 코드와 선행 결과를 연결한다. 구현 단위를 나누거나 하나로 유지한 이유와 판단에 사용한 동작·책임·검증 경계를 설명한다.

## 작업 목록과 선행 관계

| 구현 ID | 상태 | 개발 결과 | 선행 결과 | 문서 |
| --- | --- | --- | --- | --- |
| impl-001 | pending | 구현할 동작 | 설계 계약 | [구현 문서](implementation/impl-001.md) |

선행 결과가 필요한 이유와 결정된 수행 방식·제약을 설명한다. 계획과 실제 수행은 구분한다.

## 공유 변경과 통합 결정

공통 파일·인터페이스의 변경 책임과 연결 방법, 재사용·제외 범위 및 선택 근거를 설명한다.

## 검증과 완료 판단

구현별 검증 책임과 공통 검증 범위, 필요한 환경과 완료 판단 조건을 설명한다. 실제 검증 결과는 개별 구현 결과로 연결한다.

## 구현 결과의 위치

- [impl-001 구현 결과](implementation/impl-001.md#구현-결과): 실제 결과와 남은 사항 요약
```

개별 문서는 구현 지시와 실제 결과를 함께 보존한다. 빈 절을 채우기 위한 문서가 아니라 실제 구현을 설명하는 데 필요한 절을 사용한다.

```markdown
# Implementation impl-001: 작업 제목

## 목적·선행 조건

관련 요구사항·설계와 선행 결과를 연결하고, 달성할 동작을 설명한다.

## 변경 범위와 개발 내용

- 대상 코드와 변경할 동작
- 유지해야 할 공개 계약과 제약

## 완료 조건과 검증

| 완료 조건 | 확인 방법 |
| --- | --- |
| 관찰 가능한 기대 동작 | 해당 동작을 확인할 테스트 또는 실행 절차 |

## 구현 결과

### rev-01

**입력과 구현 의도**

적용한 계약·선행 결과와 이번 구현 목표를 설명한다. 사용자 제약과 착수 시 확인한 기존 변경을 기록한다.

**구성과 주요 판단**

책임·호출 흐름·재사용 구조를 설명하고, 확인한 사실과 중요한 선택의 이유를 연결한다.

**실제 변경**
```
