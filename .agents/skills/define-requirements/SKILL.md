# 요구사항 정의

사용자 요청을 목적, 범위와 기대 결과로 정리해 이후 설계·구현·검증의 판단 기준을 만든다.

1. 플레이북이나 호출자가 지정한 작업 디렉터리, 사용자 요청과 관련 자료를 확인한다. 작업 디렉터리가 불분명하면 임의로 선택하지 말고 확인한다.
2. 현재 문제와 해결 목적을 정리하고, 이번 작업에 포함할 범위와 제외할 범위를 필요한 만큼 명시한다.
3. 확인된 사실, 검증이 필요한 가정, 반드시 지켜야 할 제약을 구분한다. 구체적인 구현 방식은 설계 단계에 맡기되 사용자가 지정한 기술이나 방식은 요구사항 또는 제약으로 보존한다.
4. 기대 결과와 달성 여부를 판단할 관찰 가능한 기준을 정한다. 사용자 요청에 없는 기능이나 수치 목표를 임의로 확정하지 않는다.
5. 미확정 사항을 기록한다. 관련 자료로 확인할 수 없고 목적·범위·성공 기준을 크게 바꾸는 질문은 사용자에게 확인한다. 나머지는 미확정 상태로 남기고 추정해 확정하지 않는다.
6. 작업 디렉터리의 `requirements.md`에 아래 작성 관점을 반영한다. 기존 문서가 있으면 확인한 뒤 갱신한다.
7. [state-mgmt](../state-mgmt/SKILL.md)로 요구사항 작업을 등록하거나 기존 작업을 갱신하고 `requirements.md`를 연결한다. 이후 설계를 진행할 목적·범위·성공 기준이 충분하면 `complete`로 기록한다. 방향을 바꿀 핵심 질문이 남아 있으면 완료로 처리하지 않는다.
8. 목적이나 가정이 변경되면 요구사항 문서를 갱신한다.

## 작성할 내용

목적·가정·기대 결과를 판단하는 데 필요한 내용을 아래 관점으로 정리한다. 이미 충분히 드러난 내용은 별도 절로 반복하지 않는다.

- **현재 상태와 배경:** 작업이 제기된 상황과 해결하려는 문제를 설명한다.
- **목적:** 작업을 수행하는 이유와 궁극적으로 만들려는 변화를 정의한다.
- **출발 가정:** 확인된 사실과 검증이 필요한 가정을 구분한다.
- **기대 결과와 목표 달성 기준:** 작업 후 기대하는 상태와 달성 여부를 판단할 근거를 정리한다.
- **육하원칙에 따른 맥락:** 누가, 언제, 어디서, 무엇을, 왜, 어떻게 중 빠진 맥락을 확인하는 데 필요한 관점을 활용한다.
- **미확정 사항:** 아직 답하지 못한 질문을 기록한다. 모르는 내용을 추정해 확정하지 않는다.

초기 접근 방향은 기록하되 구체적인 구현 방식은 설계 단계에서 발전시킨다. 같은 내용은 중복 작성하기보다 관련 항목을 참조한다.
