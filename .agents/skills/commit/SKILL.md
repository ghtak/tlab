# 커밋

시작할 때 [커밋 가이드](../../../docs/agent/commit/index.md)를 읽고 작업 단위와 메시지 형식을 적용한다.
경로는 이 `SKILL.md`가 있는 디렉터리를 기준으로 해석한다.

커밋 요청은 검증 이후의 작업으로 취급한다. 테스트·정적 검사·리뷰를 별도로 실행하거나 검증 근거를 커밋의 선행 조건으로 요구하지 않는다.

## 수행

1. 사용자 요청 범위와 `git status`, staged·unstaged diff, 관련 미추적 파일을 확인한다. 관련 코드·테스트·spec 문서를 하나의 작업으로 묶고 관계없는 변경은 분리한다.
2. 작업의 주목적에 맞춰 `<유형>: <변경 내용>` 메시지를 정한다. 구성·메시지 제안만 요청받았다면 여기까지 정리한다.
3. 실제 커밋을 요청받았다면 대상 파일이나 변경 부분을 명시해 스테이징하고 최종 staged diff를 확인한 뒤 커밋한다. 기존 staged 변경도 이번 대상인지 확인하며, 무관한 변경을 포함하거나 임의로 스테이징 해제하지 않는다. 같은 파일의 변경이 섞여 안전하게 분리하기 어려우면 범위를 확인한다.
4. 생성한 커밋 해시·메시지와 남은 변경을 보고한다. 커밋 실패 시 원인을 확인하고 커밋 처리 범위에서 해결 가능한 조치 후 재시도한다. hook은 그대로 실행하며, 검증 실패로 코드 수정이 필요하면 원인을 보고하고 별도 작업으로 돌린다. hook이나 검사를 우회하지 않는다.

기존 커밋 수정·이력 재작성·원격 push는 별도 요청 범위에서만 수행한다.
