# 간단한 검증 구성 생성

플레이북이 지정한 작업 디렉터리 안에 검증 절차를 작성하고 실행 결과를 별도 문서에 기록한다.

1. 프로젝트 문서와 코드를 조사해 검증 대상, 실행 방법, 기존 테스트·조작 도구, 필요한 환경과 격리 방법을 확인한다. 확인할 수 없는 내용은 추측하지 않는다.
2. 작업 디렉터리가 지정되지 않았으면 플레이북 또는 호출자로부터 확인한다. 기존 검증 구성이 있으면 재사용하거나 필요한 부분만 보완한다. 작업 디렉터리 아래 `verification/procedure.md`에 검증 절차를 작성한다.
3. 절차 문서에 검증 대상, 준비 조건과 실행 명령, 준비 완료 확인 방법, 실제 사용 경로를 통한 검증 절차, 기대 결과와 정리 방법을 적는다. 내부 구현보다 사용자나 호출자가 관찰할 수 있는 동작을 확인하고, 파일·데이터 등 관련 부작용도 함께 확인한다. 검증 실행이 만든 임시 자원만 정리하고 결과 증거는 보존한다.
4. 기존 도구와 명령을 우선 사용한다. 스크립트나 기능별 문서는 실제 필요할 때만 추가하고, 추가한 파일의 사용법을 절차 문서에 적는다.
5. 구현 전 준비 단계에서는 실행 가능한 기존 동작만 확인하고 신규 기능의 실행은 구현 후로 남긴다. 구현 후에는 생성한 절차로 대표 기능 하나를 실제 실행해 준비부터 검증과 정리까지 확인한다. 실패하면 원인을 기록하고 가능한 범위에서 절차를 수정해 다시 확인한다. 실행할 수 없다면 미검증 범위와 이유를 보고하고, 검증되지 않은 절차를 확인된 것처럼 기록하지 않는다.
6. 작업 디렉터리의 `verification/result.md`에 절차 문서의 상대 경로, 실제 실행 내용과 관찰 결과, 실패 및 미검증 범위와 사유를 기록한다. `state-mgmt`로 검증 작업을 등록하거나 기존 작업을 갱신하고 결과 문서를 연결한다. 검증을 마쳤으면 `complete`, 진행 중이거나 검증하지 못했다면 실제 상태에 맞게 기록한다. 기존 작업 ID와 상태는 확인하고 보존한다.

실행 결과, 남은 제약과 검증 문서의 경로를 보고한다. 실제 프로젝트 동작을 임의로 변경해 검증을 통과시키지 않는다.
